# /develop — single entry, intent-routed orchestration

You orchestrate; **agents implement**. Never write production/test code or design assets yourself — dispatch the `coder` / `tester` / `reviewer` / `security-auditor` / `designer` agents via the Agent tool. You MAY read code and run verification/git commands.

All skill-internal reasoning is yours; everything shown to the user is **繁體中文（台灣）**.

## §0 Intent fork (do this FIRST — never skip)

Before anything else, classify the request. A misrouted design request must NEVER fall into the code Fix Cycle, and vice versa.

| Intent     | Signals                                                                                                                                | Route                                                                                          |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **CODE**   | implement / add / fix / refactor / build / test / review a feature; anything touching `extension/` `pwa/` `worker/` source             | → load `references/code-cycle.md`, run that lifecycle                                          |
| **DESIGN** | "make a favicon / logo / app icon / OG image / banner"; "design a brand"; "I don't like the colors / want to explore visual direction" | → load `references/design.md`, run that orchestration                                          |
| **MIXED**  | a code feature that also needs a new screen's visual mockup                                                                            | → run the CODE lifecycle; it dispatches the `designer` agent inline at the Phase-1 mockup gate |

If genuinely ambiguous, ask ONE clarifying question (AskUserQuestion) before loading a reference. When the route is clear, **`Read` the matching reference file and follow it** — it carries the full phase-by-phase workflow.

## §1 Hard rules (both routes)

- **Never write code or design assets directly.** Dispatch agents. Two exceptions you edit yourself (Edit tool, then `pnpm exec prettier --write <that file>`, then a Fix Cycle Log line): changes `.claude/rules/global.md` exempts from the workflow — pure comment / doc wording, no executable code touched — and resolving a mechanical base-update conflict (re-inserting an existing `CHANGELOG.md` bullet or `frontend.md` twin-table row, or a ≤ 5-line test-file conflict that only moves existing text — `references/code-cycle.md` → "Updating uncommitted work onto a moved main"). The run file `.claude/runs/<slug>/PLAN.md` (§2) is the one file you write and update yourself as a matter of course — it is a process record, not code.
- **Code Modification Workflow is mandatory** (`.claude/rules/global.md`): every code change — regardless of size — goes through coder → typecheck → tester → review → fix. It has **two sanctioned forms**: the **full cycle** (default) and **fix mode** — the lightweight path defined in `references/code-cycle.md` → "Mode Selection: fix mode vs full cycle": same workflow, reduced ceremony, available only when that section's mechanical eligibility conditions ALL hold. "Too small to review" is still never a reason to skip review — fix mode still runs coder → verify → regression test → CRITICAL-only review. Only the user explicitly saying "skip review" / "just write the code" bypasses it, for that task only.
- **Scope tagging.** Every code work-item is `frontend`, `backend`, or `config` (CI workflows, `wrangler.toml`, any `package.json`, `pnpm-lock.yaml` — repo configuration with no runtime code). When dispatching a `coder` / `tester` / `reviewer` agent, pass `scope` so it reads the right rules (`frontend.md` / `backend.md`; neither for `config`) and runs the right commands. A full-stack feature splits into separate scoped dispatches.
- **Agents dispatched via the Agent tool are non-interactive** — they cannot pause for the user. YOU hold every user gate (the decision gate, the goldfish decision on the plan, the GO gate on the plan, verify-before-test, SUGGESTION decisions, commit) in this session (in fix mode the decision gate, the GO gate and the commit gate are the only user gates — the other three do not occur). Do not push a user gate into an agent prompt.
- **Triage before proposing.** `Read .claude/rules/change-triage.md` before surfacing any unsolicited "X could be improved" item — SUGGESTION findings, follow-up items surfaced mid-run, opportunistic cleanups. P2 items and non-goals are not raised at all; a P0/P1 must carry `file:line`, the consequence of leaving it unfixed, and whether a failing check can be written.
- **Progress tracking (mandatory).** From the plan presentation onward — the Stop Block that holds the GO gate already prints it — keep a TodoWrite checklist of the phases and update it (✅ / ⏳ / ⬜) so the user always sees progress. If TodoWrite is unavailable, render the same checklist inline. On the code route, every Stop Block after GO also re-copies the checklist into `PLAN.md` → `## 計畫` (§2), so a later session can resume from it.

## §2 Stop discipline (both routes)

- **Decisions first, then the plan, then the GO gate — two stops before anything writes.** Every run — feature, bug, refactor, design — settles its open decisions BEFORE the execution plan is written, and presents that plan before any agent that writes is dispatched. The order is fixed: analysis (the code route's Phase 1 steps 1–7, the design route's brief) → **decision gate** → branch / worktree set up (`references/code-cycle.md` → Phase 0b) → `PLAN.md` draft written → **execution plan** → **goldfish plan review** (code route, full cycle only: `references/code-cycle.md` → Phase 1 "Goldfish plan review" — a fresh-context agent reads the draft, you classify its findings as 🟢 建議修 / 🟡 可修可不修 / 🔴 不成立, the user chooses) → **GO gate** → `PLAN.md` marked 已 GO → first dispatch.
  - **Decision gate.** The analysis closes with 「需要你決定的事」 — the numbered open decisions, each with a sentence or two of context, the options, the recommendation and its reason; the last is always 「工作目錄」 (where the work happens and what the branch is called; `references/code-cycle.md` → Phase 0). Ask them in AskUserQuestion batches of ≤ 4 with NO GO question in any batch. No branch is created, switched or renamed, no worktree opened, and nothing else written before the 「工作目錄」 answer. When the analysis finds no open decision, 「工作目錄」 is still asked, alone. An answer that changes the analysis sends it back for another round; the gate closes only when every item has an answer.
  - **Execution plan + GO gate.** With the decisions settled and 0b done, present the execution plan written against them — the settled answers restated, never re-asked. Planning is collaborative: iterate with the user until the plan is what they want. Execution starts ONLY on an explicit **GO**, given in either form: the 「GO，開始執行」 option of the AskUserQuestion that closes the plan presentation (its other option is 「修改計畫」), or a chat message that is NOTHING BUT that token — `GO`, `go`, `Go`, 「開始」 or the option text itself 「GO，開始執行」, trailing punctuation allowed, nothing else in the message. A message that merely contains the word (「開始之前，第二點改成 PATCH」, "go ahead but drop the second file") is NOT GO. The gate has exactly three outcomes: **GO** → mark `PLAN.md` 已 GO (below), then execute; an **explicit abandon** (「取消」, 「不做了」, 「不用了」, "cancel", or the 「修改計畫」 option followed by a message saying to stop) → end the run with a Stop Block stating that nothing was written, no agent dispatched, and that the branch / worktree set up at the decision gate is left as it is — name it, since it is no longer what Phase 0a found; **anything else** — a question, a partial agreement, a remark on one item — is feedback on the plan: revise it and present it again. Silence is never GO. The plan may be short — fix mode and the bug fast-path reduce it to the **short plan** defined in `references/code-cycle.md` → "Fix-mode flow" — but neither stop is skipped. Three exemptions only: the Phase 1 mockup gate (`references/code-cycle.md` → Phase 1 step 7 — the `.pen` mockup is part of the plan, and the user opts into it by answering that gate's own question), the design route's Add-icon mode for a straightforward icon as `references/design.md` → Mode 2 pins it, and the autonomous-run fold below.
  - **`PLAN.md` — the run file (code route only).** After Phase 0b the orchestrator itself writes `.claude/runs/<slug>/PLAN.md` as a DRAFT (`<slug>` = the branch slug; the folder is git-tracked, not ignored, so a WIP commit can carry it and it survives a session change in the same checkout) and on GO marks it final, in 繁體中文, with exactly five parts: a header (分支、工作目錄的絕對路徑、基準 commit、模式、狀態 — `狀態：草稿` from the draft until GO, then `狀態：已 GO`; the goldfish reviews the draft, and a `狀態：草稿` file found by Phase 0a resumes before GO), `## 決定` (every answer from the decision gate and from every later gate — the goldfish choice, verify-before-test feedback, SUGGESTION choices — one line each, the user's wording quoted), `## 計畫` (the execution plan, as presented and then as GO'd, followed by the phase checklist, re-copied at every Stop Block), `## 金魚審查` (each round's three-light table and the user's choice; `未執行：fix mode` when skipped), and `## Fix Cycle Log` (appended per round, `references/code-cycle.md` → Phase 4; whenever the session may stop mid-phase — a usage limit, a session change — it also gets a `接續點` entry: agents still out and what they may have left on disk, decisions awaiting the user, the next phase's first step). Nothing else: no evidence rule, no per-end sections, no status beyond the 草稿／已 GO line — this repo has one developer, and the file exists for one reason: a session that dies or has to move can resume from it instead of re-planning (`references/code-cycle.md` → Phase 0a step 3). It never goes into a commit on its own; the commit gate asks whether to delete it or let it ride in the feature commit (Phase 8). The design route keeps no run file.
- **After GO, run autonomously.** Do NOT stop merely to ask "可以進下一階段嗎" — continue. Stop ONLY for: a **user choice** (which SUGGESTION fixes; whether to commit/push; design direction), a **manual verification** the user must perform (verify-before-test gate; CRITICAL security findings), or a **blocker** (architecture/security problem invalidating the plan).
- **CRITICAL code findings are auto-fixed without asking.**

**Stop Block (mandatory at every stop).** Every pause MUST end with this block — a silent stop, or one that only says "完成了，要繼續嗎？", is a defect:

```
## 📍 目前進度
[the TodoWrite checklist — ✅ / ⏳ / ⬜ per phase]

## 👉 接下來需要你做的事
[the ONE concrete action the user must take now, as explicit options]
```

A command or script the user must run goes INSIDE the 👉 section, never only in the analysis above it — a later message (an agent's return) can push the analysis out of view.

**Decision prompts use AskUserQuestion.** Whenever the stop is a _choice_ (which SUGGESTIONs to take, how to commit, a direction or scope call…), issue it via the AskUserQuestion tool with the choices as options — never only as "回覆 A／B／C" text. The Stop Block still renders (progress + context); AskUserQuestion carries the actual question. Independent decisions may be batched into one call (≤ 4 questions). Free-form feedback (what is wrong after a manual verification) stays text; the verify-before-test gate's own options follow `references/code-cycle.md` Phase 3 step 3.

**Autonomous runs (user unreachable).** When the session is non-interactive, or a gate's AskUserQuestion gets no reply: adopt 🟢 TL-recommended SUGGESTIONs and skip 🔴 ones; fold the GO gate and the verify-before-test gate into their machine-verifiable acceptance checks where the spec already pins them, stating the fold and its reason at the moment of folding. Every folded gate and every decision taken is disclosed with a one-line reason in the final report and re-presented for ratification at the commit gate — which remains an explicit user question in every mode.

## §3 Agent dispatch quick-reference

| Agent              | Use for                                           | Key inputs                                                                                                                                                            |
| ------------------ | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `coder`            | production code                                   | `scope`, `requirements`, `files`, `mode` (production/research-only)                                                                                                   |
| `tester`           | tests                                             | `scope`, `target`, `scope_intent`, `change_summary` (+ actual diff)                                                                                                   |
| `reviewer`         | code review                                       | `scope`, `target`, `business_logic`                                                                                                                                   |
| `security-auditor` | post-feature security scan                        | `scope` (full/secrets/deps/code/extension/crypto/api/publish/invariants), `mode` (repo/changed + `base_ref`) — prefer `mode: changed` for a post-feature scan         |
| `designer`         | UI mockup or brand/SVG asset                      | `request`, `context`                                                                                                                                                  |
| `goldfish`         | fresh-context plan review (full cycle, before GO) | `persona` (`implementation-readiness` / `codebase-details` / `design-critic`), `target` = the `PLAN.md` draft's absolute path, `boundary`; never conversation context |

Parallelize across file-disjoint scopes (frontend + backend coders run concurrently); never let two concurrent agents own the same file. Each parallel prompt MUST name the files that agent owns AND the files its sibling is changing — otherwise an agent misreads the sibling's in-flight edits as its own diff. Mirror files (extension/pwa same-named pairs sharing a helper/fixture) go to a single agent, or each prompt carries the shared block verbatim plus an instruction to report cross-file consistency evidence (hash/diff). Independent verification legs also run in parallel — e.g. reviewer dispatch + E2E typecheck, or (small diffs) focused re-review + security scan — issue them in the same message. Re-review only the files changed by a fix, unless the user asks for a full re-review.

When a run dispatches coders in parallel, the `CHANGELOG.md` bullet has exactly ONE owner: name `CHANGELOG.md` in that agent's `files` and tell every sibling prompt not to touch it. The owning agent's bullet covers the whole change, both scopes — `.claude/agents/coder.md` item 4 is satisfied by the run, not by each agent. In a single-coder run, put `CHANGELOG.md` in that coder's `files` whenever the change is user-observable, so the bullet does not cost a Phase 8 round-trip. Ownership of a single-owner file (`CHANGELOG.md`, `docs/architecture.md`) is per round, not per run: when a later round — a Fix-Cycle fix, a backend redesign — changes what that file describes, put the file in THAT round's coder `files` rather than dispatching a separate copy coder or patching it yourself. Likewise, when a coder will edit a file listed in its package's `MAX_LINES_LEGACY_CEILINGS`, put that package's `eslint.config.js` in its `files` (lowering the number only) and state the file's headroom (`wc -l` vs the entry) in the prompt. When the headroom is zero or too small, the prompt names the block to extract and its new file (`references/code-cycle.md` → "Plan completeness self-check") — never "offset each added line by trimming comments", which `frontend.md` forbids and the coder will refuse.

**Dead agents — forensics before re-dispatch.** When a dispatched agent dies mid-run (API error, session limit, watchdog kill), first run `git status` / `git diff` to see what it left on disk:

- **Edits complete and mechanically verifiable** (diff matches the dispatch spec; the verify commands are runnable) → do NOT re-dispatch. Verify the work yourself (typecheck/lint/test) and adopt it, recording the salvage in the Fix Cycle Log.
- **Partial edits** → run the verify yourself (typecheck / lint / prettier / EOL) and check the diff against the spec: keep what passes, revert only what fails or cannot be checked, then dispatch a FRESH agent briefed as audit-and-complete — the kept edits named, the gaps listed — to finish, verify and summarize. Never trust the dead agent's unverified claims and never SendMessage-resume it.
- **Read-only agents** (reviewer / security-auditor / Explore) leave nothing on disk — re-dispatch immediately, unless the death was a session usage limit (HTTP 429): then run the forensics above on every writing agent first, and re-dispatch the read-only ones together once the limit resets.
- Repeated infrastructure deaths (e.g. consecutive 529s) → one long back-off (≥30 min) instead of a tight retry ladder; spend the wait on orchestrator-local work.
- A role agent type missing from the registry is not a death: dispatch `general-purpose` and have it first `Read .claude/agents/<role>.md` and follow that role definition.

## §4 References

- `references/code-cycle.md` — **mode selection (fix mode vs full cycle)** up front, then the CODE lifecycle: branch inventory (Phase 0a, resuming an existing `PLAN.md` when one is found) → requirements + risk analysis closing with 「需要你決定的事」, 「工作目錄」 last → **decision gate** → branch / worktree set up per that answer (Phase 0b, fresh from origin/main) → `.claude/runs/<slug>/PLAN.md` draft → execution plan → **goldfish plan review** (full cycle only; 🟢 建議修 / 🟡 可修可不修 / 🔴 不成立, at most one re-audit) → **GO gate** → `PLAN.md` marked 已 GO → API contract → coder → verify-before-test gate → tester → review → Fix Cycle (CRITICAL auto-fix / SUGGESTION decision with 🟢🔴 TL 建議) → cross-scope validation → security scan → commit gate (the retro question and the run-folder question ride in that same batch; on a yes the report is written before the commit) → **post-merge cleanup gate** (Phase 9: once the PR is MERGED, inventory the leftover branches / worktrees read-only, then ASK — `A 清除分支、清除 worktree、封存 session` / `B 清除分支、清除 worktree，不封存` / `C 什麼都不動作` — and never delete, remove or archive anything without that answer). Fix mode is the sanctioned lightweight path through the same workflow: decision gate + short plan + GO gate → coder → verify → one regression test → CRITICAL-only review; Phase 9 applies to it too.
- `references/design.md` — the DESIGN orchestration: triage (brand assets / add icon / style consultation) → brief → decision gate → GO gate → dispatch `designer` → Review & Deliver (integration snippets) → commit.
- `references/retro.md` — the run retrospective. **Offered exactly once per run, inside the commit-gate AskUserQuestion batch** (code route: Phase 8, fix mode included; design route: Deliver) — never auto-run, never suggested elsewhere, never re-asked. On a yes it runs **before the commit** so the report rides along in the feature's commit. Writes `.claude/reports/<MMDD_HHMM>.md` — conclusions only; proposals are applied later by `/distill`, never in-run. Load only after that yes (or a mid-run request).

Read the one the §0 fork selected. Do not preload both.
