## Backend Architecture Rules

Applies to: `worker/src/`

### Tech Stack

- Cloudflare Workers (TypeScript)
- Cloudflare KV for storage
- Hono (lightweight web framework for Workers)
- Vitest + Miniflare for testing

### Project Structure

```

├── index.ts          # Worker entry point + Hono app
├── routes/
│   ├── user.ts       # Personal settings API
```

**Layering.** A route module must never import business or security logic from a SIBLING route module — when two or more route modules need the same logic, it belongs in `services/`. That is why the verification gate lives in `services/verification.ts` rather than in `routes/verify.ts`, which now holds only the five `/verify` handlers. This is machine-enforced: an ESLint `no-restricted-imports` override in `worker/eslint.config.js`, scoped to `src/routes/**/*.ts`, blocks the `./*` and `**/routes/*` import patterns at lint time, so a new sibling import fails CI rather than depending on a reviewer catching it. (Coverage is static forms only — `import`, `import type`, `export … from`; the core rule does not inspect dynamic `import()`. That is a known boundary of the rule implementation, not an accepted usage.)

**Layering, second rule: a route module never touches KV itself.** No `c.env.KV.get/put/delete/list(...)`, no aliasing it into a local (`const kv = c.env.KV`), no destructuring it out of env (`const { KV } = c.env`), and no importing `kvKeys` from `../kv/schema`. Every KV access goes through `src/kv/*` — DATA ACCESS, one module per key family, each function `(kv: KVNamespace, …)` and one KV operation, documenting its key and TTL — or through `src/services/*` when it carries logic shared by two or more routes. Passing `c.env.KV` as an ARGUMENT stays the normal thing to do (`getFamilyRecord(c.env.KV, id)`, `readBorrowIndex(c.env.KV, id)`), and services may still touch KV directly: `writePublicSnapshot` keeps its own put because it owns the `buildSnapshot` chokepoint and the dynamic TTL, `services/verification.ts` keeps its verify / otp / verifyfail reads, `middleware/*` is outside the rule entirely. The accessors are deliberately THIN — a `"json"` read keeps its unvalidated cast, a put keeps `JSON.stringify` — so this is a chokepoint for key spelling, value encoding and TTLs, not a validation layer; the same `KVNamespace` (the counting Proxy from `middleware/kvOpCounting.ts`) flows through, so `kv_ops` accounting is unaffected. Enforcement is split between TWO mechanisms, and neither covers the other's ground — do not describe either as closing the whole door. (1) **ESLint**, in the same `src/routes/**/*.ts` override of `worker/eslint.config.js`: four `no-restricted-syntax` selectors — a method call on the binding (`c.env.KV.get(...)`; keys on the CALLEE's object being `X.KV`, which is why an argument does not fire it), a declaration alias (`const kv = c.env.KV`), an assignment alias (`kv = c.env.KV`), and a destructure (`const { KV } = c.env`) — plus a `no-restricted-imports` **`patterns`** entry (not `paths`) banning `kvKeys` from the group `**/kv/schema`, so a future nested `src/routes/sub/x.ts` importing `../../kv/schema` is caught too. Static forms only. (2) **The grep tripwire** `worker/tests/unit/kvAccessBoundary.test.ts`, which reads the route sources and asserts zero `kv.(get|put|delete|list)(` calls, zero `c.env.KV.`, zero `kvKeys` imports, plus the single-importer rule for `putPublicShelves`. That second mechanism is what pins the file-local-helper form — `async function readX(kv: KVNamespace) { kv.get(...) }` — which ESLint cannot see at all: the `kvKeys` ban does NOT close it, because such a helper can hand-write its key (`kv.put("family:" + id, …)`, or the same thing as a template literal) and import nothing. A third test, `worker/tests/unit/eslintKvBoundary.test.ts`, lints fixtures through ESLint's Node API so a selector that stops MATCHING fails CI instead of going quietly blind. Known boundary — nothing makes these red: computed access (`c.env["KV"].get(...)`, `Reflect.get(c.env, "KV")`, a dynamic `import()` of a key builder) escapes the selectors, and the grep matches a helper call only when the parameter is literally named `kv`, so a helper taking `store: KVNamespace` escapes BOTH checks. Limits of the implementations, not accepted usage.

One honest caveat, so the rule is not read as more than it is:

- **`services/` here is NOT a transport-agnostic layer.** `services/verification.ts` is deliberately HTTP-aware (it imports Hono's `Context` and returns `Response` via `verificationErrorResponse`) so that all three gate entry points emit byte-identical error shapes from one place, and it depends on `middleware/rateLimit.ts` for the shared KV counter primitives. Both are accepted trade-offs — do not "fix" them by re-splitting the gate.

### API Design

- RESTful JSON API. All responses wrapped in `{ data, error }` envelope.
- Prefix: `/api/`
- Authentication: token-based (issued on family create/join).
- All data stored as plaintext JSON in KV; access controlled by auth tokens.
- **userId is NOT a credential.** It is `sha256("moo:" + email)` — email-derived and publicly guessable. Any public endpoint that mints a token for a userId or reveals data bound to it (`POST /api/family`, `POST /api/family/:id/join`, `POST /api/auth/lookup`) MUST run the shared verification gate — `validateVerification(...)` + `verificationErrorResponse(...)` from `services/verification.ts` — before any KV write, token mint, or disclosure of family data (familyId, member count, member list). Accounts with no `verify:{user_id}` record (or `method: "none"`) pass through unchanged; that is a documented residual risk, not an oversight.
  - One deliberate exception: the terminal `409 ALREADY_IN_FAMILY` conflict is answered BEFORE the gate in both create and join. It discloses a single boolean ("this userId is in some family") to an unverified caller. Rationale — no secret can make such a request succeed, so gating first would only prompt for a PIN and burn the account's attempt ceiling before refusing anyway. Keep create and join in the same order; do not add further pre-gate disclosures.
- `POST /api/auth/lookup` reports the requirement instead of erroring: verification configured + no `verifySecret` ⇒ HTTP 200 with `{ existingFamilyId: null, memberCount: 0, requiresVerification: BoolFlag.TRUE }`. Use `isVerificationConfigured()` for that probe so only ONE verify-record read happens per request.
- Read-only gate callers pass `consumeOtp: false` (lookup does). A one-time `code` secret must only be spent by the request that acts on it — the client sends the SAME secret to lookup and then to create/join.
- The gate enforces its own per-userId attempt ceiling (`VERIFY_ATTEMPT_*` in `services/verification.ts`, KV scope `verify`, 10/hour, `429 RATE_LIMITED`). It lives inside `validateVerification`, not in handlers — a new caller of the gate inherits it automatically and MUST NOT re-implement it. **The ceiling only ever measures a WRONG guess, and is consulted only AFTER the comparison**: `matchesSecret()` runs first, and the wrong-secret branch alone calls `peekPerUserRateLimit()` + `chargePerUserRateLimit()`. So a correct secret is admitted regardless of the ceiling and charges nothing — a third party who spends the window blocks further _guessing_, never the account owner's own lookup / create / join. A wrong guess arriving when the window is already spent returns `429 RATE_LIMITED` instead of `403 VERIFICATION_FAILED` and does not write the spent counter again. Do NOT move the ceiling check back in front of the comparison. Both helpers live in `middleware/rateLimit.ts`; `consumePerUserRateLimit()` is the single-shot composition of the two and stays the path `enforcePerUserRateLimit()` takes whenever no native binding serves the window — every hourly scope (user / public-shelf / verify-write / family-write), plus borrow / bookshelf on a deployment without the bindings. Never duplicate the counting logic. Note that the gate's `verify` scope is distinct from the `verify-write` write ceiling in `routes/verify.ts` (`VERIFY_WRITE_LIMIT`, 30/hour, shared by the four authenticated verify-domain write handlers) — keep them on separate counters so wrong-guess throttling and the owner's own settings operations cannot crowd each other out. `routes/family.ts` mirrors that shape with `FAMILY_WRITE_LIMIT` (scope `family-write`, 30/hour), shared by its six authenticated write handlers (remove-member / un-kick / displayName / member-settings / transfer-ownership / endpoint) and always charged to the AUTHENTICATED caller, never to the `:uid` path param — a counter keyed on someone else's id would be a victim-facing lever. Create and join stay off it deliberately. (`POST /api/family/:id/join` no longer keeps a standalone per-userId "join" counter — that charge-every-request counter was a victim-facing DoS lever and redundant with the "verify" attempt ceiling above, which is now join's only per-userId brake.)
- The caller-scoped lockout check (`verifyfail:{userId}:{caller}`) stays BEFORE any comparison — it is caller-keyed, so it is not a victim-facing lever.
- **Owner-initiated member removal must stick (kicked tombstone).** `DELETE /api/family/:id/member/:uid`, in the owner-removes-OTHER branch only (`targetUserId !== callerId`; never self-leave, never sole-owner dissolve — leave-then-rejoin is legitimate), writes `kicked:{familyId}:{userId}` (TTL `KICKED_TOMBSTONE_TTL_SECONDS`, 6h) via the file-local `writeKickedTombstone()` helper SEQUENTIALLY AFTER the removal writes succeed, fail-open with `console.error` — a tombstone must never exist without its removal, or a live member gets locked out of reconnect. Second write site, same discriminator: the `404 MEMBER_NOT_FOUND` branch also re-kicks (idempotently) when the owner targets a non-member — that is the retry path after a half-failed removal (member already gone from the record, tombstone never written), and without it the ban could never be applied. The ban is REVERSIBLE by the owner: `DELETE /api/family/:id/kicked/:uid` (same file, on `FAMILY_WRITE_LIMIT`) deletes the key — auth → `:uid` format → write ceiling → family read → `callerId !== record.ownerId` ⇒ `403 NOT_OWNER` → unconditional `KV.delete` → `200 { cleared: BoolFlag.TRUE }`. Deliberately IDEMPOTENT and read-free: no prior get, so a userId that was never kicked answers identically and the response discloses nothing about whether a tombstone existed. It lifts the ban only — it never re-adds the member (Inv-4 intact) — and it cannot reach another family's tombstone, because the key is built from the path `:id` the caller was just proven to own. The TTL is now the UNATTENDED recovery bound, not the only remedy. `POST /api/family/:id/join` checks the tombstone AFTER the verification gate (no new pre-gate disclosure: "this userId was recently kicked" is only revealed to a caller who passed the account's own gate) and returns `403 MEMBER_REMOVED` for BOTH the new-member and existing-member-reconnect branches, including QR-token-bypass joins (a QR minted minutes before the kick must not outrank it). Clients treat `MEMBER_REMOVED` as family-gone (extension adds it to `FAMILY_GONE_ERROR_CODES`; PWA logs out) — that is what breaks the silent auto-rejoin loop. Residual, documented in `docs/architecture.md`: after TTL expiry a rejoin with the sync code is again possible (the Inv-4-sanctioned re-add path; the sync code IS the familyId and cannot rotate), and the ~60s KV propagation window cuts both ways — a join racing the kick can slip through, and a join arriving right after an un-kick can still be refused by a colo holding the stale key (retry resolves it).
- All three gate entry points are **sensitive public routes** (`sensitiveBucketFor()` / `isSensitivePublicRoute()` in `utils/routes.ts`): `POST /api/family`, `POST /api/family/:id/join`, `POST /api/auth/lookup`. Any public route where an unauthenticated caller can test a secret belongs on that tier. The classification is path-only — the rate-limit middleware runs before body parsing, so it cannot depend on whether a `verifySecret` was sent. The tier carries ONE limit (3/min/IP) but **two isolated counters**: `onboarding` (create / join, key `ratelimit:sens:{ip}`) and `lookup` (key `ratelimit:sens:lookup:{ip}`) — two keys on the SAME 3/min binding, and the same two keys with a `:{bucket}` suffix when they fall back to KV. Reason: one clean onboarding of a verified account spends 2 lookups (no-secret probe, then the same secret) + 1 create/join inside one minute from one IP, so a shared counter would 429 the first typo retry — or the second household member behind the same NAT / IPv6 /64. `rateLimitBucketFor()` in `middleware/rateLimit.ts` maps a route to `{ prefix, limit }`; add new tiers there and in `sensitiveBucketFor()`, never as a special case in the middleware body.
- **Per-minute limits run on Cloudflare's native Rate Limiting binding; hourly counters stay on KV.** `bindingForWindow(env, max, windowSec)` in `middleware/rateLimit.ts` maps (limit, 60s) to one of four bindings through the file-local `BINDING_BY_LIMIT` table: `RATE_LIMIT_60_PER_MIN` (per-IP standard tier + per-userId `borrow-list`), `RATE_LIMIT_30_PER_MIN` (`bookshelf`, `borrow-update`), `RATE_LIMIT_10_PER_MIN` (per-IP public tier + `borrow-create`), `RATE_LIMIT_3_PER_MIN` (per-IP sensitive tier, BOTH buckets). A new per-minute limit is added there and as an optional field on `Env` (`utils/env.ts`), never inline in the middleware or a handler. Keys keep the counter prefixes minus the window bucket, which the binding owns — `{tierPrefix}:{ip}` and `ratelimit:user:{scope}:{userId}` — so several scopes can share one binding and stay isolated. Binding semantics, accepted deliberately in exchange for zero KV operations: per Cloudflare LOCATION, eventually consistent, permissive by design, so it is not a hard bound either; no remaining count (`X-RateLimit-Remaining` is dropped on that path, `X-RateLimit-Limit` is not) and no reset time (`retryAfter` = the 60s period, not the time left in a bucket). The bindings are declared in `wrangler.toml` as `[[unsafe.bindings]]` with `type = "ratelimit"`, NOT the `[[ratelimits]]` blocks in Cloudflare's current docs: the pinned wrangler 3 rejects `ratelimits` as an unexpected field and would deploy the Worker without the bindings. Revisit when the wrangler devDependency moves to v4.
- `bindingForWindow` returning `null` means "count this one in KV", for THREE distinct reasons, each with its own log behaviour. (1) The window is not 60s — every hourly scope: SILENT, because hourly is KV by design. (2) `BINDING_BY_LIMIT` names a binding for this per-minute limit but the deployment does not carry it — a self-hoster whose wrangler.toml predates them: logs `RATE_LIMIT_BINDING_MISSING` with that binding name. (3) The window is 60s but the limit has no entry in `BINDING_BY_LIMIT` — someone raised a tier's number without adding the binding: logs the SAME line with `<unmapped:{limit}/min>` in place of a name, because a configuration mistake must be as loud as a missing binding, never silent like (1). Consequently: **adding or changing any per-minute limit means editing `BINDING_BY_LIMIT` and `wrangler.toml` in the same change** (and the `simple.limit` in wrangler.toml must equal the number in the binding NAME — the Worker resolves bindings by name only and cannot detect a mismatch at runtime). The log fires once per rate-limit CHECK, not once per request: a route guarded by both the per-IP middleware and a per-minute per-userId ceiling (`bookshelf`, `borrow-create`, `borrow-list`, `borrow-update`) emits TWO lines. Cases (2) and (3) fall back to the previous KV get-then-put counter, unchanged including both `X-RateLimit-*` headers. That routing lives in `enforcePerUserRateLimit` alone: the `peekPerUserRateLimit` / `chargePerUserRateLimit` pair — the charge-on-failure form, whose only caller outside `middleware/rateLimit.ts` today is the hourly `verify` attempt ceiling in `services/verification.ts` — never consults `bindingForWindow`, so it can neither reach a binding nor log `RATE_LIMIT_BINDING_MISSING`. Keep it for HOURLY, charge-on-failure counters only: a new per-minute ceiling MUST be enforced through `enforcePerUserRateLimit`, never through `peekPerUserRateLimit` / `chargePerUserRateLimit` / `consumePerUserRateLimit` directly (all three are exported and none of them consults `bindingForWindow`), or it stays on KV with nothing logged to say so. Every counter still on KV — the hourly per-userId scopes, the verification attempt ceiling in `services/verification.ts`, and that fallback — remains non-atomic and unserialized: a parallel burst overshoots by the caller's concurrency (there is no fixed ~2× factor), so those limits bound sequential traffic only. A hard bound stays out of scope; see `docs/architecture.md` → 已接受的殘餘風險.
- `bookCoverUrl` on `POST /api/family/:id/borrow` is stored verbatim and later rendered into an `<img src>`, so a NON-EMPTY value is validated at the handler boundary by `isAllowedCoverUrl()` from `moo-family-bookshelf-shared/config/readmoo` (https + Readmoo registrable-domain suffix + default port + base-invariance — the four conditions are spelled out under the KV table below) and rejected with `400 INVALID_COVER_URL` — an anti-tracking-beacon check that stops a family member from planting a URL that leaks every viewer's IP/UA to a third party. It runs BEFORE `enforcePerUserRateLimit`, like every other format check: a malformed request must not burn the caller's quota. The rule lives in `shared/` so the Worker's acceptance and the PWA's CSP `img-src` cannot drift apart. The field is OPTIONAL, classified by the file-local `normalizeBookCoverUrl()` exactly the way `sanitizeVerifySecret()` classifies `verifySecret`: absent / `null` / `""` all mean "no cover" and are accepted and stored as `""`; any other non-string is `400 INVALID_FIELDS` (a request-format error, never a whitelist rejection); only a non-empty string reaches `isAllowedCoverUrl()`. Empty must be accepted because the bookshelf aggregation sanitizes off-whitelist covers to `""` and the clients forward that verbatim — treating it as missing made such books unborrowable. `BorrowRequest.bookCoverUrl` in `kv/schema.ts` stays a non-optional `string`, so the KV value shape is unchanged and the record never carries `undefined` / `null`.
- `verifySecret` is classified at the HANDLER boundary by `sanitizeVerifySecret()` in `utils/validation.ts`, identically in all three gate entry points: absent / `null` / `""` ⇒ "not supplied" (each endpoint's documented no-secret behavior), any other non-string or longer than `VERIFY_SECRET_MAX_LENGTH` (256) ⇒ `400 INVALID_VERIFY_SECRET` via `verifySecretFormatResponse()`. A malformed body is a request-format error, never a failed verification — it must not reach `hashSecret` nor be charged against any budget.

**Public shelves are a single-writer domain.** `publicshelves:{user_id}` is written ONLY by the four public-shelf write handlers (create / update / reset-token / delete) in `routes/publicShelf.ts` — the sole exception is `DELETE /api/user/:id` in `routes/user.ts`, whose whole-account teardown also `delete`s the key (a wipe, not a list write — it can resurrect nothing) — and the local `writePublicShelves()` helper is the single `put`. That helper is now a thin wrapper over `putPublicShelves()` in `kv/publicShelves.ts`, which IS exported (the data-access layer above carries a full get / put / delete for `publicshelves:{user_id}`; it does NOT give every key an accessor — see the next sentence for `public:{share_token}`, and the `services/`- / `middleware/`-only families `verifyfail:*`, `borrow:*` / `borrows:family:*` and `ratelimit:*`, which have no `src/kv/*` module at all; `docs/architecture.md` → 2.5「存取層」sets out the exceptions among the keys in its own table), so the invariant is no longer "nothing shared offers a put". It is pinned instead by a tripwire test asserting that `routes/publicShelf.ts` is the ONLY module under `worker/src/` importing `putPublicShelves` — named specifier or `import * as` / `export *` wildcard binding alike (`worker/tests/unit/kvAccessBoundary.test.ts`) — a grep-shaped check that fails CI the moment a second importer appears anywhere, services and middleware included. `public:{share_token}` deliberately has NO put accessor for the same reason it never had a shared helper: every snapshot write must go through `writePublicSnapshot` in `services/publicShelf.ts`, which owns the sanitize chokepoint and the sub-minimum-TTL rule. `PUT`/`PATCH /api/user/:id/books` READ it (one pointer get each); `PUT /api/user/:id/family-prefs` does not even read it — it writes no snapshots, so it needs no pointer (see that handler's comment in `routes/user.ts`). None of the three ever writes it. Reason: `user:{user_id}` is a read-modify-write blob with no CAS and KV cross-colo reads can lag ~60s, so while the shelf list lived inside that record a books sync from a second device could roll a revoked token back to life and re-publish a snapshot the owner had just deleted. Migration is LAZY and handler-only: when the pointer key is absent, readers fall back to the legacy `user:{id}.publicSharing` field via the pure `resolvePublicShelves(pointer, legacy)` in `services/publicShelf.ts` (a non-null pointer record always wins, INCLUDING an empty `shelves` array — that means "migrated, no shelves"), and the next public-shelf WRITE creates it. Never migrate from the books path or from a GET handler. Once migrated, the PUT books handler omits the legacy field from the rebuilt record (PATCH strips it from the carried-over record) and it evaporates. Orthogonal to the writer domain but load-bearing on the same path: `buildSnapshot` in `services/publicShelf.ts` is the URL-whitelist sanitize CHOKEPOINT that EVERY `public:{share_token}` snapshot writer funnels through (the books-path refresh plus publicShelf create / update / reset-token), so a `user:{id}` record poisoned before the whitelist existed can never mint a fresh poisoned snapshot — do not remove it, and never write a snapshot around it. It scrubs BOTH attacker-controlled URL fields of a book, and every site named below handles the PAIR, never just one: `coverUrl` through `sanitizeCoverUrl` (rendered as `<img src>` — a tracking beacon that loads by itself) and `readmooUrl` through `sanitizeReadmooUrl` (rendered as a clickable `<a href>` — a phishing / arbitrary-redirect lure that lands the viewer on attacker-controlled content and discloses their IP / User-Agent to it, but only once the viewer clicks; the Referer header does NOT leak, because all four render sites pair `target="_blank"` with `rel="noopener noreferrer"` and `noreferrer` suppresses that header outright — the attribute is load-bearing there, not boilerplate). Both helpers live in `utils/validation.ts`, both blank an off-whitelist value to `""` rather than rejecting the payload (`""` is already a legitimate stored value), and both delegate to `moo-family-bookshelf-shared/config/readmoo` — `isAllowedCoverUrl` / `isAllowedBookUrl`, two deliberately separate exports over ONE file-local core. Same rule today — FOUR conditions: https, a Readmoo registrable domain from `READMOO_COVER_DOMAINS`, the default port, and base-invariance (`new URL(url, probe).href` must equal the standalone `href`). That fourth condition exists because the Worker validates a STRING while the browser resolves that same string against the RENDERING document, so without it the two can name different destinations: the verified exploit puts `https:readmoo.com/../../public/x` in a book field, which passes the first three checks (host reads as `readmoo.com` standalone) and then navigates the viewer to the PWA's OWN origin at `/public/x#invite=…`, where the SPA fallback unconditionally clears the stored session and pre-fills the attacker's sync code. The criterion is base-SENSITIVITY, not a missing literal `//` — WHATWG treats `\` as `/` for a special scheme, so 0 or 1 slash-ish character after `https:` is base-sensitive and rejected while 2 or more is base-independent, which means spellings such as `https:\\readmoo.com/x` or `https:/\readmoo.com/x` are genuine absolute Readmoo URLs and stay ALLOWED; never re-derive this as a `//` test (see the core's JSDoc). Different trust boundaries, so either can be tightened later without silently changing the other; keep the core shared so the two cannot drift. Neither may be rebuilt on `isReadmooHost`: that exact-match list holds only the web-app hosts (`next.` / `read.`), while every legitimate book link lives on the apex `readmoo.com`, so it would blank all of them. That chokepoint has TWO READ-side twins: the family-bookshelf aggregation in `routes/bookshelf.ts`, so a dormant pre-whitelist record cannot beacon or phish family members while waiting for a write that may never come; and the public snapshot read `GET /api/public/:shareToken` in `routes/publicShelf.ts`, where a snapshot minted before the whitelist existed keeps its foreign URLs until the shelf is refreshed — for a PERMANENT shelf, indefinitely. The public one is a response transform only: that handler's no-KV-writes invariant still holds. It also makes the mitigation independent of the PWA CSP, which is not always delivered (`pwa/public/_headers` only applies on hosts that parse it, e.g. Cloudflare Pages — a self-hosted PWA on GitHub Pages / S3 / nginx ships no `img-src` whitelist), so the CSP is defence in depth for covers rather than the load-bearing control — and no help at all for book links, since `img-src` never constrained a navigation. All three sites are load-bearing — keep them; `worker/tests/integration/bookshelfPrivacy.test.ts` pins the aggregation twin. The three books WRITE paths in `routes/user.ts` run the same pair (`parseBooks` on PUT, the PATCH rebuild, the family-prefs rebuild), keeping fresh poison out of `user:{id}` and lazily scrubbing whatever a pre-whitelist write left there; the render side adds a client-only backstop (`safeCoverUrl` / `safeBookUrl` in `extension/src/dialog/` and `pwa/src/utils/`) that also covers an un-upgraded self-hosted Worker. Still uncovered on this path: `routes/borrow.ts` copies the client-sent `bookCoverUrl` into `borrow:{requestId}` verbatim (no TTL) and returns it verbatim on list; `borrow:{requestId}` carries no book-link field at all, so `readmooUrl` has no borrow-side exposure.

The read-side liveness guard in `GET /api/public/:shareToken` now validates ALL snapshots (was: permanent-only) against that pointer key — same `shelfId`, same `shareToken`, and an expiry that does not OUTLIVE the shelf's; any drift ⇒ 404 byte-identical to an unknown token — falling back to the legacy field only for un-migrated owners. The expiry half is MONOTONIC, not strict equality (`snapshotOutlivesShelf()` in `routes/publicShelf.ts`, where `null` = permanent = +∞): a snapshot promising LONGER than its shelf — including a permanent snapshot of a now time-limited shelf — is dead, because that is the direction an orphan or a rolled-back snapshot drifts in; a snapshot promising SHORTER stays readable and simply dies at its own earlier deadline unless refreshed, which is what a rewrite from a stale pointer read right after the owner EXTENDED the deadline looks like (strict equality used to 404 that, i.e. deny access the owner had just widened). Guard order stays snapshot miss → `expiresAt` backstop → liveness, and the handler still performs NO KV writes. Cost per public hit that holds a valid token: ONE extra small KV read (`publicshelves:{id}`) for a migrated owner, TWO for an un-migrated one — that pointer miss plus a fallback read of the FULL `user:{id}` books record, which is not small — and the second read disappears on their first shelf write. Residuals, stated honestly: LWW races remain possible WITHIN the writer domain (the owner's own concurrent shelf operations against each other), un-migrated users keep the old behavior until their first shelf write, a freshly rotated token can 404 for up to ~60s on a colo holding a stale pointer list (fail-closed, self-healing) — a window that now also applies to time-limited shelves — and the single-writer guarantee itself only holds once the pointer key is VISIBLE to the reading colo: for ~60s after the FIRST migration write (the revoke that creates the key) a colo holding a negative-cached miss still falls back to the legacy field, so a books save racing that one-time-per-user window can leave the link briefly readable; and element-level KV corruption stays unvalidated (container shape only — see the `resolvePublicShelves` JSDoc), fail-closed in every constructible case.

**The family borrow index is the single source of truth, and its history is capped.** `borrows:family:{family_id}` holds the full `BorrowRequest[]`; `borrow:{request_id}` is only a `BorrowPointer` (`{ familyId }`), read by `PATCH /api/borrow/:requestId` — which starts from a bare requestId — to find the owning family. It used to be the other way round (records under `borrow:{id}`, ids in the index), which cost one KV read per historical entry on every list AND on the create handler's duplicate check. All of it lives in `services/borrowIndex.ts`, not in `routes/borrow.ts`, because `routes/family.ts` and `routes/user.ts` need it too (the departure settlement below) and a route module may not import a sibling route module; unlike `services/verification.ts` this one is HTTP-agnostic — it takes a `KVNamespace` and returns plain data. Exactly TWO functions write `borrows:family:{family_id}` — `writeBorrowIndex()`, the only put, and `deleteBorrowIndex()`, the only delete — reached from exactly FOUR entry points: create and PATCH in `routes/borrow.ts`, member removal in `routes/family.ts`, and account deletion in `routes/user.ts` (grep `kvKeys.borrow` / `borrowsByFamily` — no other module touches either key). `trimBorrowIndex()` is what bounds the growth — the resulting size is "live requests + at most `BORROW_HISTORY_KEEP` PER BORROWER", not a constant: every PENDING/LENT record is kept at any count (they are still actionable — evicting one would strand a lent book), and of the TERMINAL statuses (`TERMINAL_BORROW_STATUSES` = RETURNED / REJECTED / CANCELLED) only the newest `BORROW_HISTORY_KEEP` (20, `kv/schema.ts`) of EACH `borrowerId` survive, ordered by `updatedAt`, tie-broken by `createdAt` and then by the index's own order; evicted records leave the index AND their `borrow:{id}` key is deleted. Grouping by borrower is deliberate: a family-wide cap let the most active member's finished borrows evict ANOTHER member's history — one member destroying another's records on a shared value — so the family-level bound is (members × 20) terminal records plus every live one, and a member can only ever push out their own oldest entries. That cap is user-visible (each member's finished-borrow history shows at most 20 items — stated in `CHANGELOG.md`), and it replaces the old "acceptable only while the index stays under 20 entries" comment, which asked a reviewer to enforce a bound nothing measured. The trim cannot touch a LIVE record, so the create handler carries the rest of the bound: `BORROW_MAX_PENDING_PER_BORROWER` (20, `kv/schema.ts`) caps how many PENDING requests one borrower may have open — counted from the caller's OWN records in the index that was just read, after the membership and `DUPLICATE_REQUEST` checks, answered `409 TOO_MANY_PENDING_REQUESTS` with no write — and four length caps in `utils/validation.ts` (`bookId` / `bookTitle` ≤ 200, `bookAuthor` ≤ 100, non-empty `bookCoverUrl` ≤ 2048) bound each record's SIZE with `400 INVALID_FIELDS`, in the SAME guard slot as the string-type check so a format error never reaches the rate-limit charge. Both are measured on the caller's own data, so neither is a lever a third party can spend (Inv-6). **Departure reclaims, and the cap depends on it.** A per-`borrowerId` cap bounds nothing on its own, because a borrowerId is free to mint (security finding F-1): a sync-code holder joins with a fresh userId, opens `BORROW_MAX_PENDING_PER_BORROWER` requests, leaves — every one becomes a CANCELLED record under a borrowerId that will never write again, so its group is never trimmed — and repeats, growing the one 25 MiB index with no reclaim path until create / PATCH / member removal all 500. So BORROWER COUNT is bounded at both exits. `settleDepartingBorrower(kv, familyId, userId)` runs wherever a member leaves — the removal handler in `routes/family.ts` (self-leave and kick alike, still BEFORE the family record changes, still `500 BORROW_CLEANUP_FAILED` and no removal if it throws) and the multi-member branch of `DELETE /api/user/:id` (fail-open there: an account deletion has no "nothing happened" answer to give). It first CANCELS every PENDING the departing member is either side of (`borrowerId` or `ownerId`; LENT untouched — the book may still be out), then REMOVES from the index every TERMINAL record whose `borrowerId` is that member, deleting those pointers fail-open under the same `BORROW_POINTER_DELETE_FAILED` tag; note `writeBorrowIndex` deletes only what ITS OWN trim dropped, so a caller that filters records out must delete their pointers itself. Records where the leaver was the OWNER STAY — they are the remaining borrower's history, they count against THAT borrower's allowance, and purging them would let a leaver destroy a family member's records. Nothing changed ⇒ nothing written (a legacy index stays legacy). `deleteBorrowIndex(kv, familyId)` is the dissolve half: sole-owner leave in `routes/family.ts` and sole-member account deletion in `routes/user.ts` both call it fail-open (`BORROW_INDEX_DELETE_FAILED`) BEFORE dropping the family record, so a failure leaves a retryable state rather than a family-less index; it deletes every pointer the stored index names (BOTH shapes, read once for the ids only — never through `readBorrowIndex`, whose legacy fan-out would buy records nobody needs) and then the index key. Write ORDER is load-bearing twice, and both rules point the same way — never leave an index entry whose pointer is missing, always prefer an orphan pointer: `writeBorrowIndex` puts the index BEFORE deleting evicted pointers, and create writes the POINTER before the index. An orphan pointer is one wasted key that no reader can see, plus a `404 REQUEST_NOT_FOUND` on a PATCH of a record that is gone from the index anyway (trim) or was never listed at all (create, where the caller's retry just mints a fresh UUID). The forbidden state is the reverse: an index entry with no pointer is a PENDING ghost BOTH parties see and neither can act on (PATCH cannot resolve its family), the trim never removes it because PENDING is exempt, and it permanently blocks re-requesting that book via `DUPLICATE_REQUEST`. Those eviction deletes are additionally FAIL-OPEN — `.catch` → `console.error("BORROW_POINTER_DELETE_FAILED", …)`, the `writeKickedTombstone` pattern — because the index put has already landed and a failed cleanup delete must not turn a persisted write into a 500. Migration off the legacy shape is LAZY and WRITE-PATH ONLY: `readBorrowIndex()` serves a legacy `string[]` index by fanning out one last time, the next write rewrites the new shape, and `GET /api/family/:id/borrow` handles BOTH shapes with NO KV write at all — never migrate from the list handler. Legacy `borrow:{id}` values are full records and are never rewritten: they carry `familyId`, which is the only field `readBorrowPointer()` reads, so after migration the value is a stale copy no reader consults and rewriting it would spend a KV write per record for nothing. That one field is validated with `isValidFamilyId` rather than merely checked for a non-empty string, and PATCH additionally refuses (`404 REQUEST_NOT_FOUND`, no write) when the pointer and the record found inside the index disagree on `familyId` — defence in depth on both halves, because the pointer's value picks the KEY of the read-modify-write the handler is about to perform. Residual, accepted: the index is a read-modify-write of ONE key with no CAS, so two concurrent writers on the SAME family lose one another's update (last put wins) — previously the same race dropped a requestId from the index, now it can drop a whole record or a status change. See `docs/architecture.md` → 已接受的殘餘風險, together with the remaining borrow residuals (PATCH never re-checks membership; a fail-open cleanup that throws still leaves an orphan pointer, or — on dissolve — an orphan index no write path will visit again).

Platform constraint: Cloudflare KV rejects any `expirationTtl` below 60 seconds ("Invalid expiration_ttl, must be at least 60"). Fixed TTLs in this table already satisfy that. The floor is the shared production constant `KV_MIN_TTL_SECONDS` in `kv/schema.ts`; the test-side mock keeps a deliberately independent copy (see below). A DYNAMICALLY computed TTL must respect the floor in one of two ways, both in use today: the `public:{share_token}` snapshot (`services/publicShelf.ts`) treats a remaining lifetime under 60s as already expired — delete the key instead of putting with a sub-minimum TTL, which would throw and surface as a 500; the per-userId counter write (`chargePerUserRateLimit` in `middleware/rateLimit.ts`) clamps its derived `windowSec * 2` up to the floor with `Math.max`, so a future rate window under 30s yields a slightly longer-lived counter instead of a rejected put (a unit test drives a sub-30s window through the charge path and pins the clamped TTL at 60). The test-side KV mock (`worker/tests/helpers/mockKv.ts`) enforces this floor at `put` time — and is deliberately STRICTER than the platform for non-integer TTLs — so a regressed dynamic TTL fails unit tests instead of only surfacing against real KV. The tripwire only covers TTL values some test actually produces: a NEW derived TTL stays unchecked until a test drives it below the floor.

### Coding Conventions

- No `any` type. Strict TypeScript.
- Keep handler functions thin — extract business logic into helpers.
- Validate all inputs at the handler level before processing.
- Return proper HTTP status codes (400, 401, 403, 404, 429, 500).
- Error responses include machine-readable `code` field.
