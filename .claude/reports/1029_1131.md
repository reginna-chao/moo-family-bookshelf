## 2. 卡點與摩擦

- **U1**（使用者，工作目錄回答）：「這個涉及 PIN 碼設定，可能會跟另外一個正在進行的項目衝突，請你先暫停所有工作，之後可能會從 origin/main 重新分析」。Phase 0a 有列 `git worktree list`，但沒有把其他 worktree 的分支（`fix/secret-entry-extension-iframe`）和本 run 要碰的檔案對照，使用者得自己判斷有沒有衝突。重新分析後確認 #363 已合併且檔案零重疊，多花一輪。
- **U2**（使用者，兩次）：「我還是不懂為什麼要改? 是資安問題嗎」、「pepper 到底是甚麼」。分析一開始用了 salt／pepper／HMAC／離線猜等詞，沒有先用一段白話說「誰拿得到什麼、能做什麼、今天有沒有人打得進來」。P2 安全設計題的決策關卡前應先有這一段。
- **G1**（計畫錯誤，coder 抓到）：計畫把升級函式寫成 `(env, userId, record)`，但 v2 是 HMAC(pepper, salt+**明文密鑰**)，從 v1 雜湊算不出來，必須多收剛比對成功的 `secret`。三隻金魚兩輪都沒抓到；coder 回報時標為「與 PLAN 不同，請確認」。雜湊遷移類計畫要明寫「重算需要哪些輸入」。
- **G2**（金魚）：Round 1 共 13 項（2 Blocker：寫回競態會鎖死帳號、503 契約沒定），Round 2 再 6 項全採用。「計畫完整性」教訓再次重現：契約面（型別聯集、五條 route 的 `responses`）、文件化不變式（`verification.ts:363`、三張 KV 表）、其他寫入者（`/verify/prompted`、`DELETE /user`）都是計畫第一版沒列的。
- **G3**（本機驗證）：`wrangler dev` 改 `.dev.vars` 不會重載，三次情境要停掉重啟兩次；停掉時 `Stop-Process` workerd 會被 wrangler 重生，要用 `Win32_Process` 命令列找 wrangler 的 node 再殺。另外 `wrangler kv key put --local` 在這個 repo 要加 `--preview`（binding 同時有 `id` 與 `preview_id`，dev Worker 讀 preview），與 `.claude/rules/backend.md` → Local-dev facts 寫的「needs `--preview false`」相反。
- **G4**（工具）：auto mode 分類器擋下「`cp .dev.vars` 並 `cat` 內容」；拆成只 `cp` 不顯示內容就通過。
- **G5**（security-auditor WARNING）：殘餘風險 (a) 的接受理由只考慮本人；知道舊 PIN 的第三方也能觸發升級寫回讓舊 PIN 復活。計畫寫殘餘風險時預設了「當事人只有本人」，審查才補上攻擊者視角。
