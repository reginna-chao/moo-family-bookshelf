## 2. 卡點與摩擦

- **G1：兩個 PR 各自全綠，合併後 main 變紅。** #226 加入行數上限時，清單是依 `026863a` 量的；#223 比它早合併，而且改長了清單上的 4 個檔案。#226 的 CI 跑在舊的 base 上，所以沒看到。main 沒有分支保護，GitHub 也不會要求 PR 在合併前更新到最新的 main。這次是使用者要開始拆 `SettingsPage.tsx` 時，我量行數才發現的，不是 CI 通知。
- **G2：「上限必須等於實際行數」的防護測試，把這類衝突放大了。** 只要兩個 PR 同時改到清單上同一個檔案的行數，不管變長還是變短，合併後都會變紅。清單上的 48 個檔案正好是最大、最常被修改的檔案。這個取捨是 0929_1113 那次為了強制「只准變小」而做的，當時沒有考慮到平行 PR 的情況。
- **G3：fix mode 的 tester 規則，沒有考慮「失敗的檢查已經存在」這種情況。** 規則要求寫「一個修正前紅、修正後綠的回歸測試」。這次現成的防護測試在 main 上本來就是紅的，修正後轉綠，再寫一個只會重複。所以這次沒有派 tester，並在完成報告裡揭露。
- **G4：0929_1113 的 Phase 8 在 commit 前做了 base 檢查，但 PR 開出來之後、合併之前，main 又前進了。** 流程只要求在 commit 前檢查 base，合併這一步完全由使用者在 GitHub 上操作，orchestrator 看不到。

## 3. 改進提案

### Flow-structural（L#）

- **L0929_1600-1**：`target=.claude/skills/develop/references/code-cycle.md | sketch=Phase 8 的完成報告補一條：PR 改動的規則會依賴「目前檔案內容」時（例如依行數列清單、依檔案內容產生快照），要提醒使用者在合併前把 PR 更新到最新的 main 並重跑 CI，或確認分支保護已經開啟 | status=proposed`
- **L0929_1600-2**：`target=.claude/skills/develop/references/code-cycle.md | sketch=fix-mode tester 規則補一句：如果已經有一個測試在 base 上是紅的、修正後轉綠，它就是這次的回歸檢查，不必另外寫；完成報告要寫出那個測試的名稱和前後結果 | status=proposed`

### 執行槓桿（E#）

- **E1**：開始一個以 main 為 base 的新 run 時，先跑一次該 scope 的 lint 和測試，確認 base 本身是綠的。這次如果沒先量行數，拆 `SettingsPage.tsx` 的 coder 會帶著一個不是它造成的紅燈開工。
- **E2**：清單上的檔案，被其他 PR 修改時很容易互相衝突。如果之後常常發生，可以考慮把防護測試從「等於」放寬成「不超過，而且差距在某個範圍內」。現在先靠分支保護，等實際觀察到頻率再決定。
