### 執行槓桿（no flow gap）

- **E1**：coder 回傳帶機械 probe（lockfile 閉包、install script 掃描）時，reviewer 與 security-auditor 的 prompt 直接附 probe 路徑與結論，要求「重跑驗證、不要重寫」；本 run 可省兩支腳本與約 1 萬行 lockfile 的重讀。與上份報告 E2 同型，第二次出現（G5）。
- **E2**：突變檢查副本在 tester 派工前由 orchestrator 先規劃「每個負向斷言各自需要哪份副本才會紅」，寫進 tester prompt；本 run 第一份計畫只有一份副本，靠金魚重審補第二份，S1／S3 又各補一份，共四份。
- **E3**：聚焦重審在「處方逐字落地、diff 超過 5 行」時仍必須派（規則如此），本 run 第二次聚焦重審（220 秒、6.6 萬 token）確實又找到 S3，值得；但 S3 的修正我改用 orchestrator 自核處方落地而不再派第三輪，因為處方已含 reviewer 自己的 probe 結果——「reviewer 處方附 probe 證據」可當作自核的門檻。
- **E4**：base 更新時先看 `git diff --name-only HEAD origin/main`，無重疊就 `--ff-only`，再 `pnpm install --frozen-lockfile` 與 root verify；本 run 兩次都照 `1028_0915.md` L1028_0915-2 的草案做，零重工。

## 4. Skill / Agent 增減建議

- **goldfish**：兩隻 persona 的獨有發現仍各自存在（readiness：lockfile 外溢處置、正向對照、grep 範圍；codebase：`allowBuilds` 的 spawn-sync 鏈、wrangler 版本退回的理由）；重審又抓到一條 Major。保留兩隻與一次重審上限。
- **reviewer**：對 regex 做 probe 的習慣是這次價值最高的動作，兩輪各找出一組漏洞；建議把「對 denylist 做對抗性 probe」寫進 tester（L1），讓 reviewer 回到驗證者角色。
- **tester**：三次派工中後兩次是套處方，每次仍花 30 萬 token 等級；若 L1 採納，第一次就能一次到位。
- **security-auditor**：`secrets` + `deps` 的供應鏈推演（frozen-lockfile → integrity → `pnpm exec` 不下載；剩餘未釘的 pnpm 本身與 Node major）是這次報告裡最有用的段落，保留；但 deps 面向與 reviewer R7／R10 重疊（E1）。
- 不建議新增 agent。
