## 2. 卡點與摩擦

- **G1 — 併發負載未先校準，差點拿到空頭綠燈**：orchestrator 初次 probe 用 16 次併發（2 輪 ×8）才碰到 1 次失敗；tester 進一步校準後指出 **8× 在修前也不會失敗**，唯一可靠閘門是 24×（修前基線 22/24，兩次皆 `:276 expected 1, got 0`）。若沿用 8× 當驗收門檻，「修後全綠」完全不構成證據。
- **G2 — 報告的症狀只是類別的一例**：任務指名的 `keeps the later-issued write's result…`（`expected 2, got 1`）在本次 80+ 次跑中一次都沒重現；實際重現的是同檔另一個測試（`stays silent when a mid-flight write fails after the shelf was revoked`，`expected 1, got 0`），後續在 extension 鏡像檔也重現（1/16）。根因是**整檔共用的就緒訊號**，只修指名 test 會留下已證實會倒的同類 flake。
- **G3 — mirror 檔案並行派工必然漂移**：round 1 對 pwa / extension 各派一個 tester，兩者雖自行協調了 helper 名稱，仍留下 3 處漂移（理由註解措辭不同、`// getBy, not findBy` 只寫在 pwa 兩檔、create-view 測試一邊轉換一邊不轉換），全部要靠 round 2 對齊（rework_rt 1）。第二個修復改以單一 tester 承擔三組套件，零漂移。
- **G4 — 驗證階段炸出第二個 load-sensitive flake，且更嚴重**：最終驗證的 6 次全 workspace run 中有 2 次倒在 `FamilyShelfPage > Load More (Wave G) > click Load More appends pageSize to visible count`（**timeout in 30000ms**，實耗 39480ms / 33191ms），與第一個修復無關。同一測試在 6 次 run 中從 4.3s 到 39.5s，9 倍漂移。根因是 production 的 `useLoadMore` 預設 `pageSize = 100` 讓 component 測試必須渲染 100–200 列，**縮小 fixture 無法解決**。使用者決定一併修，改以 repo 內既有慣例（`extension/src/dialog/PersonalShelf.tsx` 的 `pageSize?` prop）注入小頁長；12× 併發 A/B 實測最差耗時 24756ms（預算 82%）→ 8664ms（29%）。
- **G5 — subagent 中途因 API 529 死亡**：第二個 coder 在完成兩個檔案的編輯、跑完兩個套件後、於 e2e typecheck 階段死亡。code-cycle 現行規則要求一律重派全新 agent；但其產出是 3 個機械式 hunk ×2 檔、可完整閱讀並由 orchestrator 自行跑 typecheck/lint/測試驗證，重派只會產生 no-op 或 churn。實際採取「自行完整驗證」，全綠。
- **G6 — reviewer 的覆蓋缺失宣稱前提錯誤，orchestrator 未查證就轉成處方**：reviewer 的 S3 指 `items.length === pageSize` 邊界無人覆蓋（引用 table 的第 3–4 列），orchestrator 認同並寫進 tester prompt；tester 查出該 table 的**第 1 列**早已是 `{ items: 100, pageSize: 100, expectedHasMore: false }`，並用 mutation test（把 `<` 改成 `<=`）證明正是那一列在守門，正確地跳過不新增。
- **U# — 無**：六個決策點（兩次範圍、兩次 SUGGESTION 取捨、production 註解、是否跑 security scan）使用者皆採 TL 建議，無糾正、無回退。
