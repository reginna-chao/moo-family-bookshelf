## 2. 卡點與摩擦

**U（使用者修正）**：無。三次 AskUserQuestion 皆選建議選項。

**G1（跨 scope 共用新檔造成 coder 序列化）**：frontend coder 要 import backend coder 才建立的
`shared/src/borrow/history.ts`，兩個 coder 無法平行。序列化是正確選擇（平行會讓 frontend 的 typecheck
撞到不存在的檔），代價約 6 分鐘。**教訓**：需求裡一旦出現「新的 shared 模組 + 兩端消費者」，dispatch
順序是固定的——建立者先、消費者後；把 shared 模組的精確匯出清單寫進第二個 prompt，第二個 coder 就不用
再讀檔推敲。

**G2（prompt 內的路徑黑名單與項目清單互相矛盾）**：frontend coder 的前言寫「不得動 `.claude/`」，第 4 項卻
要求編輯 `.claude/rules/frontend.md`。coder 自行判斷黑名單是在保護 backend 已 staged 的檔，做了正確的事並
回報。**教訓**：owned files 用白名單逐檔列出，不要同時寫一條會蓋過白名單的目錄黑名單。

**G3（UI 間距沒寫進規格，多一輪 SendMessage）**：規格只說「灰色小字、清單上方」，沒說與上方按鈕的間距；
coder 自己發現「按鈕與提示之間沒空隙」並標為 nit，多一次來回。**教訓**：新增 UI 元素的規格要寫「與相鄰
元素的間距沿用 X」。

**G4（客戶端顯示、伺服器執行的數字需要自架者揭露）**：reviewer 抓到 CHANGELOG 沒寫「自架者伺服器也要
更新，否則畫面寫 50、實際仍裁 20」。這是一個可泛化的類型：任何「常數在 shared、UI 負責顯示、Worker 負責
執行」的變更，客戶端與自架伺服器都可能版本錯位。`shared/src/borrow/messages.ts` 對 `TOO_MANY_PENDING_REQUESTS`
刻意不寫數字就是同一個顧慮。目前 `user-facing-copy.md` 的檢查清單沒有這一項。

**G5（`CLAUDE.md` 是 symlink）**：prompt 要求編輯 `CLAUDE.md` 與 `AGENTS.md`；coder 以 `git ls-files -s`
發現 `CLAUDE.md` 是 mode 120000 的 symlink，只改 `AGENTS.md`。無損失，記下以免下次 prompt 再列兩個檔。
