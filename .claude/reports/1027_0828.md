## 2. 卡點與摩擦

- **U1**：使用者在 coder 因 429 中斷後說「請再試一次」。這不是修正，是中斷後的重啟指令。
- **G1 — coder 死亡後的接手**：第一個 coder 把程式碼全部改完、正要跑 prettier 時被 429 切斷，eslint 上限、frontend.md、AGENTS.md、CHANGELOG 都沒做。SKILL.md §3 的規則寫「partial → revert the leftovers, then re-dispatch audit-and-complete: inventory what landed」，前半句叫人還原、後半句叫人盤點已落地的東西，兩句互相矛盾。實際做法是自己跑 typecheck／lint／prettier／EOL 驗證後保留程式碼，再派一個 coder 補完缺口，沒有還原任何東西。結果正確，但規則文字需要修。
- **G2 — main 連續前進兩次，兩次都撞到同兩個文件**：#395 和 #397 各加一條 CHANGELOG bullet 並改 twin 表一列。code-cycle.md 的更新食譜只寫了 CHANGELOG.md 的 patch 流程，frontend.md 的 twin 表要靠同一招自己推。第二次衝突還多一層：我這邊把 PinInput 列搬到另一個分類群組，upstream 改的是舊位置旁邊的 BookRow 列，3-way 無法自動合。兩次都是純文件、機械解決，但各花一輪。
- **G3 — issue 文字與程式不符**：#385 說 Extension「輸入非數字時」顯示「PIN 碼只能包含數字」，實際上非數字會被整次擋掉，那句只在空白送出時出現。Phase 1 的 premise check 抓到了，沒有影響實作。
- **G4 — 文件 coder 寫出的 twin 表描述被 reviewer 推翻**：補完文件的 coder 寫「送出流程來自 shared」，reviewer 對照程式發現 shared 只提供規則與序列化，送出流程是兩邊各自實作，而且漏了三項使用者看得到的平台差異。多一輪 coder。
- **G5 — 刻意序列化的檢查**：完整測試套件和 E2E typecheck 依序跑，不和 agent 的執行重疊，避免 CPU 搶奪造成假性 timeout（記憶中已有先例）。這是正確取捨，但 tester 627 秒加上套件 110 秒成為瓶頸。
