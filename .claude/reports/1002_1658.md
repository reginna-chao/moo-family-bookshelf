## 2. 卡點與摩擦

使用者沒有更正或中斷（U# 無）。

- **G1 — Phase 1 沒有列出「誰會寫版本、誰會寫它保護的資料」，C1 到審查才出現。** 設計是「PUT 成功後記下回應的新 `lastUpdated`」。記下新版本的同時，`extension/src/dialog/useApplySyncResult.ts` 仍會把書單換成同步讀到的舊值而沿用版本，於是畫面拿著新版本配舊分享設定。這個洞是「採用新版本」這一步打開的，需求分析時只看了儲存的兩個呼叫點，沒有 grep `savedRawPayload` 的其他寫入者。代價是一整輪 coder → tester → re-review。
- **G2 — 重組規則是 orchestrator 寫進 coder prompt 的，其中一格寫錯，成了 C2。** prompt 寫「其他書伺服器有就取伺服器的值，沒有就保留本地」。「沒改過、伺服器已經沒有」這一格保留本地分享值，等於把別處移除的書以分享寫回。規則有四格（dirty × 伺服器有／沒有），寫 prompt 時只想了三格。reviewer 第二輪和 auditor 第一輪各自找到，再花一輪。
- **G3 — orchestrator 把沒查證的前提寫進 prompt：「舊版 Worker 的 PUT 回應是 `{ ok }`」。** 依據只有 client 的回傳型別 `ApiResponse<{ ok: boolean }>`，沒有看 `worker/src/routes/user.ts` 的歷史。reviewer 第二輪查 git 才指出 PUT 從第一版就回 `{ data: record }`。這個前提已經進了 3 處註解、`docs/architecture.md` 一列和 10 個測試名稱，清理用掉 1 次只改註解的 coder 派工，外加 tester 改名。
- **G4 — 同一個發現，兩個 agent 給的等級不同。** auditor 把 C2 的情境標成 INFO（理由是修正前就會發生），reviewer 標成 CRITICAL（理由是新的重組函式是它的載體，而且會通過新的版本檢查）。orchestrator 等 reviewer 回來才處置，沒有先開 issue，所以沒有重複，但如果只有 auditor 的報告，這項會被當成範圍外。
- **G5 — reviewer 比 tester 早 6 分鐘回來，C1 的修正只能等。** 平行派工時正式程式碼凍結，reviewer 663 秒回報 CRITICAL，tester 1042 秒才結束。等待期間 orchestrator 先讀 `useApplySyncResult.ts`、`syncBooks.ts` 確認前提並問了 S2，所以修正派工是一次送出，沒有多一輪。
- **G6 — run 期間 main 前進（#264），`CHANGELOG.md` 同一段衝突。** 變更只 stage 沒 commit，`git apply` 因上下文不同失敗，改由 orchestrator 用 Edit 把同一條 bullet 原文放回去。和 `1002_1506` 的 G5 是同一件事。
- **G7 — verify-before-test gate 驗不到這次修的行為。** 整份 PUT 只在少數條件下發生（改超過 1000 本、改到伺服器不認得的書），衝突又需要第二台裝置剛好插進來，手動無法穩定重現。gate 實際確認的是「一般儲存和初次同步沒壞」，衝突行為全靠自動化測試。
- **G8 — tester 一度把測試輸出寫到 worktree 外（`.claude/worktrees/t2.txt`）。** 它自己發現並移走。之後的 prompt 都加了「暫存輸出放 `$TEMP`」。
- **G9 — 讀 issue 花了 3 次呼叫。** PowerShell 的 `gh issue view --comments` 和 Bash 的同一指令都沒有輸出，改成 `--json … > 檔案` 再 Read 才拿到內容。
