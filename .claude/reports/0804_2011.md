## 2. 卡點與摩擦

- **G1 — reviewer dispatch 中途 API 斷線**：Round 2 聚焦 re-review 第一次派出即死於
  "Connection closed mid-response"，部分輸出不可用，整段重派（~7 分鐘 + 一次完整
  review 的 token 損耗）。處置：直接重派全新 agent，不嘗試 SendMessage 續接半殘狀態。
- **G2 — 更名連動造成強制序列化**：R2 把 `resetLegacyFallbackWarnings` 更名為
  `resetScrapeWarnings`（無 alias），coder 不可動測試 → typecheck 紅兩行 → 必須再派
  tester 同步。已知且可控（紅點清單由 coder 明確交接），但這是本 run 唯一無法平行的
  修復輪。
- **G3 — 測試自斷言假象**：`BorrowTab.test.tsx` 的錯誤文案斷言是對自建 mock Error
  斷言而非 production 字串，S15 改了 production 文案該測試照樣綠。由 Round-2 coder
  意外發現，tester 補上唯一打在 production 上的文案斷言（`readmooLend.test.ts`）。
- **U（正向記錄）— 使用者提供的兩項事實有誤，開工前核對抓到**：worker CORS regex
  本已放行 `next.readmoo.com`（非故障原因）；Firefox manifest 由 Chrome dist 整包
  繼承（不需另改邏輯）。印證「verify in code first」規則的價值，計畫因此少走兩步。

## 3. 改進提案

- **L0804_2011-1**：`target=.claude/rules/frontend.md | sketch=Node 腳本目錄（extension/scripts/ 等）必須被某個 tsconfig project 涵蓋進 pnpm typecheck，新增腳本時檢查 | status=proposed`
  — 本 run 發現 verify-selectors.ts 700 行重寫在 CI 完全零靜態檢查，靠 review 才補上
  `tsconfig.scripts.json`。
- **L0804_2011-2**：`target=.claude/rules/test.md | sketch=E2E anti-drift 規則擴充到 component 測試：使用者可見文案的斷言至少要有一條直接打在 production 拋出點上，mock 自斷言不算數 | status=proposed`
  — G3 的教訓；現行規則只涵蓋 E2E helper 的常數 import。
- **E1**：production export 更名時，coder prompt 內先寫明「預期紅掉的測試與新名」，
  tester prompt 直接帶新名清單——本 run 這樣做把 G2 的損耗壓到一輪，維持此習慣。
- **E2**：子代理死於 API 錯誤時一律重派全新 agent（帶原 prompt + 「前次中斷重跑」註記），
  不續接半殘輸出。
- **E3**：修復輪若是 reviewer 處方箋被逐字落地的 ≤5 行改動，由 orchestrator 自核 diff
  取代再派一輪 re-review（本 run Round 3 如此，省一次完整 dispatch）。
