## 2. 卡點與摩擦

- **G1 第 1 批 retro 的兩個改法都生效**：（a）量測算法修正後本批基準從 issue 表的 98 變成 93（issue 表把「空一行接 export」的 JSDoc 也算進去，而修正版把它們視為漏量的另一類——兩邊各有盲點，修正版的數字才是 coder 實際處理的清單）；（b）coder 不跑完整測試、由 orchestrator 序列跑，coder 牆鐘從 28,658 秒降到 997 秒，reviewer 與 pwa 全套測試得以平行。
- **G2 reviewer 抓到的仍是「搬進規則檔的句子不完整」**：第 1 批是「過度概括」（CRITICAL），本批是「漏列例外」（SUGGESTION，CI 測試已擋）。兩批都落在同一個位置——`frontend.md` 新寫的句子——而不是程式碼或 docs。這是這類 run 的固定風險點。
- **G3 parity 測試把 extension 檔拉進本批**：`useSyncCodeHostVerdict.parity.test.ts` 連註解一起比對兩份雙胞胎，所以 pwa 批次必須同步改 extension 那一份。coder 依 prompt 的預判處理正確；但其他沒有測試強制的雙胞胎（`safeCoverUrl.ts`、`safeBookUrl.ts`、`publicShareMessages.ts` 等）的 extension 版本現在還寫著「四個檔案刻意保持相同」的舊長註解，與 PWA 版文字已不同（程式碼仍相同），留給第 4 批處理。
- **U1 使用者問「目前所有檔案都改完了嗎? 比我想像中的少」**（第 1 批 PR 開啟前）：使用者對「六批、每批一個 PR」的分批結構沒有即時畫面。回答後以表格列出六批與各自的區塊數，之後每個 Stop Block 都帶這張進度表。

## 3. 改進提案

**Flow-structural**

- L1007_1053-1：`target=.claude/skills/develop/references/code-cycle.md | sketch=L1007_0936-1 的「註解遷移」路徑再加一條：reviewer prompt 把「新寫進 .claude/rules 的每一句」列為獨立檢查項（逐句對照程式碼：計數、條件、例外清單是否完整），因為連續兩批唯一的發現都在這裡 | status=proposed`
- 不提升：G3。`frontend.md` 新增的 twins 節已把「哪些雙胞胎有測試強制、哪些沒有」寫清楚，第 4 批 coder 讀規則即可。
- 不提升：U1。多批次任務的進度表已在 Stop Block 內，不需要流程改動。

**執行槓桿**

- E1：多批次 issue 的第一個 Stop Block 就放完整批次表（批次、目錄、區塊數、狀態），之後每個 Stop Block 更新同一張表，不要等使用者問。
- E2：第 4 批（`extension/src`）的 coder prompt 直接附上 `frontend.md` → Extension ↔ PWA twins 的清單，要求 extension 版的雙胞胎註解改成與 PWA 版逐字相同（含 `<twin-dir>` 路徑互指）。
- E3：第 3 批起 PR 內文的量測表標明「修正後算法」並附第 1 批 PR #290 說明的盲點，避免與 issue 表的數字對不上時被當成漏改。
