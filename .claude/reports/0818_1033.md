## 2 卡點與摩擦

**U1 — 使用者中斷 tester + reviewer 的平行派送（本 run 唯一使用者更正）**
兩個 Agent 呼叫同時回 `[Request interrupted by user for tool use]`，無附帶訊息。隨後 AskUserQuestion 的選擇是「我直接跑 test + 派 reviewer」，證實中斷針對的是 **tester dispatch 本身**，不是平行化。判讀：本 run 不寫任何測試，派一個 agent 只為執行 `pnpm test` 一道指令，是把 agent 當指令執行器。

**G1 — tester prompt 寫成「verify-only，禁止修改任何測試」，是流程順序倒逼出的產物**
orchestrator 為滿足 `code-cycle.md` Phase 3 的 coder→tester 順序，寫了一份約 60 行、核心約束是「**不准做你的本職工作**」的 tester prompt。這種 prompt 本身就是訊號：該階段沒有標的。正確判準是「本 run 是否有測試需撰寫或修改」，否則不該派。

**G2 — verify-before-test gate 的適用性判斷發生得太晚**
該 gate 的 rationale 明寫是「避免對未確認的行為寫測試」。本 run 不寫測試，gate 無標的。orchestrator 直到 coder 交付後才自行判斷折疊，而非在 Phase 1 認定「純重構 + 既有測試即 oracle」這條路徑從一開始就不需要它。晚判斷的代價：合併停點的設計與 tester prompt 的撰寫是同時進行的，後者因此白寫。

**G3 — 完整測試套件跑了三次（142s + 185s + 60s ≈ 387s）**
第一次撞上 `tests/unit/scraper.test.ts` 的 hook timeout flake；第二次為排除 flake；第三次為讓「全綠」涵蓋註解修正後的最終樹。前兩次可壓縮成一次目標檔案跑測。第三次是必要的（宣稱的驗證必須對應實際提交的樹）。

**G4 — `AGENTS.md` 記載的測試過濾用法不成立**
`AGENTS.md` 的 Build & Development Commands 寫 `pnpm test -- tests/unit/crypto` 為「specific」用法。實測 `pnpm test -- tests/unit/scraper.test.ts` **不過濾**，跑完整 123 檔 2470 測試（185s）。可用的形式是 `npx vitest run <path>`（實測 2 檔 104 測試僅 2.3s）。文件與現實落差 ≈ 80 倍時間成本。

## 3 改進提案

### Flow-structural

- **L0818_1033-1** — `tester` 的派送條件應是「有測試要寫或改」，而非流程順序。無測試工作時由 orchestrator 直接跑套件並回報。判準：若 tester prompt 的主要內容是禁止它改測試，就不該派它。
  `target=.claude/skills/develop/references/code-cycle.md | sketch=Phase 3 step 4 加前置條件 — dispatch tester only when tests are to be authored or modified; otherwise the orchestrator runs the suite itself | status=proposed`
  _Cut-before-add_：既有步驟的條件化，非淨增流程。

- **L0818_1033-2** — verify-before-test gate 應有明文的不適用條件，且在 Phase 1 就宣告，不在 coder 交付後臨時判斷。
  `target=.claude/skills/develop/references/code-cycle.md | sketch=Phase 3 step 3 加 N/A 條件 — when the run authors no tests (pure refactor, existing suite is the oracle), declare the fold at Phase 1 and hold ONE consolidated stop after the suite runs | status=proposed`

- **L0818_1033-3** — `AGENTS.md` 的單檔測試指令錯誤，應更正為 `npx vitest run <path>`。這是每個 run 都會踩的成本，且錯誤形式（跑完整套件）不會報錯，只是慢 80 倍，因此不會自我暴露。
  `target=AGENTS.md | sketch=Build & Development Commands — 修正 "Tests (extension, specific)" 一行；同步檢查 .claude/rules/test.md 是否有同樣寫法 | status=proposed`

### 執行槓桿（E#，無流程缺口）

- **E1** — 純結構重構先用 `npx vitest run <受影響檔>` 取快速訊號，完整套件只在最終提交前跑一次。本 run 三次完整套件（≈387s）中至少一次可省。
- **E2** — 測試失敗先分類「斷言失敗 vs hook/timeout」。hook timeout + 檔案與改動無 import 關聯 = flake 假設，用「該檔 import 了什麼」加一次重跑證偽即可，不必開 Fix Cycle。本 run 這樣處理，成本僅一次重跑。
- **E3** — 使用者已完整指定檔案、參照模式、限制與驗證指令時，Phase 1 需求確認 gate 直接折疊為假設宣告。本 run 這樣做，零返工。
- **E4** — 純註解修正（`global.md` 明列的 Fix Cycle 例外）由 orchestrator 直接以 Bash 套用，不派 coder/tester。本 run 的 S3/S5 如此處理，省下兩次 dispatch。

## 4 Skill / Agent 增減建議

- **不新增任何 agent。**
- **reviewer 產出本 run 唯一的實質發現，且是 coder 結構上不可能發現的。** S2 指出 `type OnboardingState = string` 遮蔽了 `useOnboardingFlow.ts:31` 匯出的同名真實 union，導致 `state === "creating"` 完全不受型別檢查。coder 在「逐字搬移」約束下必然原樣保留它 —— 只有以外部視角重讀全域符號的 reviewer 會撞見。同時 reviewer 正確處理了約束優先序（S1 明標「verbatim 約束優先於 sibling 對齊，coder 取捨正確」），沒有把約束造成的偏差算成缺陷。
- **`tester` 在「無測試工作」情境下無角色**，但這屬派送決策而非 agent 職責 —— 建議 `/distill` 時寫進 `code-cycle.md`（見 L0818_1033-1），**不要**寫進 `.claude/agents/tester.md`。
- **無可精簡項。** `/develop` §0 intent fork 一次命中 CODE，未出現冗餘 skill 載入。
