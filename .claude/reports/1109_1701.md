## 2. 卡點與摩擦

使用者沒有中途更正（無 U#），每個岔路都在選項裡決定。

- **G1 基準一直移動。** 開工前等前置 PR 合併；GO 之後 `origin/main` 又前進四次，其中一次和 `family.ts`／`user.ts`／`backend.md` 重疊，要 WIP commit → rebase → `reset --soft`，兩處機械衝突由 orchestrator 解。
- **G2 計畫對無密鑰帳號的說法錯了（金魚 Round 1）。** 計畫寫「`none`／`code` 帳號行為不變」，但沿用 `enforceCurrentSecret` 會一併帶進過期紀錄檢查與目前 token 檢查，兩者都對所有帳號生效。三個 persona 中有兩個獨立抓到。
- **G3 確認插在沒有 CAS 的讀改寫中間（金魚 Round 2）。** 計畫原本把密鑰確認放在讀 `family:{id}` 之後、寫回之前，讓覆寫空檔多出約 3 次依序的 KV 往返。改成在讀家庭紀錄之前確認。Round 2 再次出現 Major。
- **G4 一個 UI 修正引出兩輪後續。** tester 回報「轉移時打錯 PIN 輸入框不清空」→ 改成被拒後重新掛載 → 複審發現重新掛載會移除原本有焦點的 secure frame，焦點落回宿主頁面 → 加 `autoFocus`，並用 E2E 在真的 Chrome 證實（拿掉修正就失敗）。重新掛載與焦點的關係，計畫階段沒有人想到。
- **G5 公開 PR 會描述尚未修的行為。** 第一版只修離開與轉移，回歸測試與規則文字卻寫著另外兩個流程「被拒後不聚焦」。commit 關卡前由 orchestrator 自己發現，最後四個流程一起修。

## 4. Skill / Agent 增減建議

- 金魚審查保留：兩輪約 98 萬 token，是最大的消耗，但 Round 1 修正了計畫對無密鑰帳號的錯誤說法，Round 2 抓到讀改寫空檔，兩者都會影響實作。
- 複審（focused re-review）這次在 Round 2 抓到焦點問題，是整個 run 最有價值的一次派工；小範圍的修正也值得派。
- 平行派 3 個 tester（worker／extension／pwa）各自跑變異驗證，沒有互相干擾，可以繼續這樣分。
