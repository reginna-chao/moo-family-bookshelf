## 2. 卡點與摩擦

使用者沒有更正或中斷（U# 無）。

- **G1 — fix mode 預測失準，差 1 行升級。** 預估是「加一個判斷」，量測結果 41 行。`pwa/src/App.tsx` 釘在 `max-lines` 上限，新增 2 行就得刪註解來抵銷，`--numstat` 兩欄都算，光 `App.tsx` 就 12 + 17 = 29 行；Prettier 把加長的 import 拆成 4 行又多 3 行；`pwa/eslint.config.js` 降上限再算 2 行。真正的邏輯變更不到 15 行。
- **G2 — 以 fix mode 開場後升級，Phase 1 的風險分析從頭到尾沒做。** fix mode 把 Phase 1 收成開場的一段話，升級後「已完成的 phase 不重跑」，所以這次 run 沒有任何一步去列「還有哪些呼叫點會登出」。S1（`useLeaveFamily.ts:54,69`、`useDeleteAccount.ts:44` 的非點擊登出）是 reviewer 和 auditor 在事後各自找到的，多花了一整輪 coder → tester → re-review → 重掃。另外，這次開場訊息只寫了一行進度，沒有照 fix mode 規定重述根因 `file:line` 和驗收條件。
- **G3 — 預期變紅清單漏掉「空轉變綠」的測試。** S1 把判斷改成 `isLiveSession` 後，coder 回報 11 個測試變紅。tester 補 fixture 時才發現另外 7 個斷言「沒有登出」的測試（`INVALID_TOKEN`、`NETWORK_ERROR`、5 個 prototype-chain 案例）在那個中間狀態是因為判斷提早返回才通過，沒有走到要測的程式。跑測試看紅燈找不到這種案例。
- **G4 — `App.test.tsx` 把 `useAuth` 整個 mock 掉，localStorage 沒有 session 鍵。** 正式程式的判斷一旦開始讀 storage，fixture 就和正式環境脫節。這次是 orchestrator 在派 coder 前自己 grep 才提前發現，並寫進 coder 和 tester 的 prompt。
- **G5 — run 期間 main 前進（#261），`CHANGELOG.md` 同一段衝突。** 變更只 stage 沒 commit，`merge --ff-only` 會因為同檔案被拒絕。處理方式是 restore `CHANGELOG.md` → 快轉 → orchestrator 用 Edit 把同一條 bullet 原文放回去 → 重跑完整驗證。每個平行 run 都往 `## 未釋出` → `### 問題修正` 的最後一行加 bullet，所以只要 main 有前進就一定衝突。
- **G6 — 第一輪安全掃描和 review 平行跑，兩者回報同一個發現。** auditor 的 INFO 1 和 reviewer 的 S1 是同一件事。兩個獨立來源一致讓採用的判斷很容易，但 Fix Cycle 之後還得再掃一次，總共 2 次掃描。
- **G7 — 重掃才找到範圍外的 P0（#263）。** 第一輪掃描的 prompt 把影響範圍列到 `client.ts`、`useAuth.ts`，沒有列 Worker；第二輪 auditor 自己追到 `worker/src/routes/family.ts` 才發現「join 已送出就無法撤銷」。

## 3. 改進提案

### Flow-structural

- **L1002_1506-1** `target=.claude/skills/develop/references/code-cycle.md | sketch=fix mode 預測時，若要改的檔案已在 max-lines legacy ceiling 上（行數等於上限），直接預測為完整流程：新增的每一行都要靠刪除抵銷，numstat 兩欄都算 | status=proposed`
- **L1002_1506-2** `target=.claude/skills/develop/references/code-cycle.md | sketch=fix mode 在第一次 coder 回來就升級時，補做 Phase 1 第 6 步的精簡版（列出同一類問題的其他呼叫點／觸發路徑）再進 tester，不要等 reviewer 事後找 | status=proposed`
- **L1002_1506-3** `target=.claude/skills/develop/references/code-cycle.md（Fix-round handoffs → Behavior handoff） | sketch=修正若新增「提早返回」的判斷，交接清單除了預期變紅的測試，還要列出同一路徑上只做否定斷言（not called / 仍保留 session）的測試，要求 tester 確認它們有走到判斷之後 | status=proposed`
- **L1002_1506-4** `target=.claude/rules/test.md | sketch=整個 mock 掉 useAuth 的元件測試，fixture 要同步寫入正式程式會寫的 storage 鍵（現在 App.test.tsx 的 setMockSession 是範例） | status=proposed`
- **L1002_1506-5** `target=.claude/skills/develop/references/code-cycle.md（Phase 8 第 4 步） | sketch=main 前進且 CHANGELOG.md 衝突時的固定做法：restore CHANGELOG → 快轉 → 把同一條 bullet 原文接在最後 → 重跑 scope verify；註明這是搬移既有文案，不需要回派 coder | status=proposed`
- 第一輪 review 與安全掃描平行：`不提升：規則已允許，這次兩個來源互相印證的價值大於多掃一次的成本`。

### 執行槓桿

- **E1** 派 coder 前先對目標檔案跑 `wc -l` 並對照 `eslint.config.js` 的上限，這次是做了才知道要在 prompt 裡寫「不能變長」，但沒有把它反映到模式預測上。
- **E2** 正式程式的判斷要讀新的外部狀態（storage、全域變數）時，派 coder 前先 grep 測試的 mock 方式，把會脫節的 fixture 寫進 prompt。這次有做，省掉一輪「tester 發現大量紅燈 → 回頭釐清」。
- **E3** 安全掃描的 prompt 列影響範圍時，登入／登出／成員資格類的變更要把對應的 Worker route 一起列進去，不要只列前端檔案。
- **E4** 轉述 agent 的附帶觀察給使用者前，先對照它發生在哪個中間狀態。這次把 G3 的 7 個空轉測試說成「第一輪改完後」，實際上是 S1 的 coder 改完、fixture 還沒補的那段時間。

## 4. Skill / Agent 增減建議

- **不新增 skill 或 agent。**
- `coder` 的回報格式可以加一欄「這次變更讓哪些既有測試的前提改變」（對應 L-3），比事後由 tester 發現便宜。屬於 `.claude/agents/coder.md` 的小幅增補，等 L-3 是否採用再決定。
