## 2. 卡點與摩擦

- **G1：CRITICAL 是 orchestrator 自己的規格造成的。** 使用者選的是「先記起來，讀到後再合併」，我把合併方式寫成 XOR（翻轉），但沒有在需求確認時提出來。reviewer 用實際情境重現：讀取失敗時，畫面上所有書都顯示沒有標記，使用者這時點擊一定是想「加上」；XOR 卻會翻掉伺服器上已有的標記，並送出刪除。tester 照規格寫了一個「伺服器已有的標記會被移除」的測試，等於把 bug 固定成規格，後來又得改掉。
- **G2：tester 做 mutation check 時，reviewer 同時在讀 production 檔。** 依 code-cycle Phase 3 step 4，這兩個 agent 平行跑。tester 在工作目錄直接改壞 `shared/src/familyShelf/prefsModel.ts`，再從備份還原；reviewer 的 tsx 探測剛好落在這個窗口，一度看到舊的 XOR 結果。reviewer 自己發現了，比對 index blob 後重跑，所以沒有造成誤判，但這是運氣。
- **G3：上一個 run（#208）的 retro 和 main 上另一個 session 的 retro 用了同一個檔名 `0924_1322.md`。** merge 時出現 add/add，而且兩份報告裡的 `L0924_1322-n` 編號也會混在一起。最後把本 session 那份改成 `0924_1323` 才解決。retro.md 的命名規則只保證「同一個 session 內不會重複」，沒有處理不同 session 在同一分鐘各寫一份的情況。
- **G4：使用者跳過了測試前的手動驗證。** 這次由兩端 hook 各一個完整重現 #219 的測試取代，並用 mutation check 確認測試抓得到錯。手動驗證步驟需要 dev worker 的帳號和 DevTools 的請求封鎖，操作成本高，這可能就是被跳過的原因。
