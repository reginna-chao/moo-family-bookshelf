## 2. 卡點與摩擦

- **U1**：決策關卡第 2 題的推薦（官方不受理人工救援）被使用者推翻：「發送求救→寄信驗證→確認本人驗證→解除，看起來目前會卡在沒有沒辦法送信驗證?」→ 追問一輪後選「改做 Email 驗證救援」。第 1 題的答案（維持無自助路徑）因此作廢，但第 1 題和第 2 題在同一批提問，使用者答第 1 題時還不知道第 2 題會改變方向。
- **U2**：run 中途使用者問「信箱那個部分要怎麼解決?」。設計文件已經在寫，但使用者看不到進度，等於把文件第 7 節用聊天重講一次。
- **G1**：提示文字改好後，coder 回報三處同類標題仍寫「手機版」；問使用者後改成「登入驗證」，又造成區塊與小標題同名、QR Code 掛在「登入驗證」底下，再問一次改「手機登入與驗證」。同一個 label 派了兩輪 coder，兩次 AskUserQuestion 本可併成一次。
- **G2**：orchestrator 依純文件例外自己寫的三份文件，事實核對找到 2 項 CRITICAL：把「刪除帳號」列為卡死原因（HEAD 的 #341 已改成連驗證一起刪）、低估重設 token 外洩的後果。寫文件時只讀了 verify／auth 的程式，沒有核對 `routes/user.ts` 的刪除路徑。
- **G3**：security-auditor 在 `worker/DEPLOY.md` 的管理者流程找到真實空窗（刪除 `verify:` 到本人重設之間），而且空窗期 token 在重設後仍有效。這是文件描述的操作程序，不是程式碼，但 Phase 6 的 scope map 對 `docs/`／`worker/DEPLOY.md` 不計 area；這次是因為 UI 字串落在 `extension/` 與 `pwa/` 兩個 area 才跑到 `full`，auditor 順便讀了文件。純文件的 run 不會觸發掃描。
- **G4**：origin/main 中途前進 1 commit（#346），`docs/architecture.md` 重疊，走 wip commit → rebase → reset --soft，無衝突，成本約一分鐘。
