## 2. 卡點與摩擦

- **G1：4 個 coder 平行拆檔，沒有互相踩到。** 做法是：
  - 每份 prompt 寫明自己負責的檔名前綴，以及另外 3 個 coder 的檔案。
  - 會重疊的兩個 `eslint.config.js` 清單不交給任何一個 coder，全部拆完後由一個收尾 coder 統一處理。
  - 平行期間，各 coder 只跑自己相關的測試，完整測試留到全部完成後再跑一次。

  這套分工值得保留。

- **G2：reviewer 讀 index 時，收尾的修改還沒 staged，因此回報了一個假的 CRITICAL。** 這次是「收尾 coder」和「reviewer」同時進行：reviewer 照指示讀 index，但清單條目的刪除當時還在工作目錄裡，所以它判定 CI 會變紅。修正方式是 staged 那份修改。「reviewer 一律讀 index」這個做法，前提是**會影響 CI 結果的修改都已經 staged**。
- **G3：拆檔讓 code-cycle.md 的敏感檔案清單失準，這次是 coder 自己發現的。** `PersonalShelfPage.tsx` 的存檔邏輯搬到 `usePersonalShelf*` 之後，fix mode 條件 4 以整個檔案為單位的清單就漏掉了這些新檔。安全掃描另外找到兩個原本就存在的缺口：登入 hook（`useLanding*`、`useQrJoin`），以及 #221 搬進 `shared/src/crypto/` 的 `deriveUserId`。三項都在這次補上了。清單以檔案路徑為準，所以程式碼一搬家，清單就可能默默失效。
- **G4：收尾 coder 把 lint 的 log 寫到 worktree 外面**（`../../ext-lint.log`），之後自己發現並刪掉了。這是 cwd 不固定時，用相對路徑重導輸出造成的。
- **G5：`.claude/worktrees/` 底下留了 3 個空資料夾**（#209、#215、#216 的工作區移除後留下的）。使用者要求「刪除相關工作區」時才發現；目前這個 session 自己的工作區，要等 session 封存後由 app 移除。
- **G6：第一次跑完整覆蓋率測試時，15 個測試檔在收集階段逾時。** 當時機器負載很高，用 `--maxWorkers=8` 重跑後全部通過。
