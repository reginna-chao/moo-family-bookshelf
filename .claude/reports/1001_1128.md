## 2. 卡點與摩擦

- **U1**（設計方向）：第一輪需求確認時，orchestrator 提的是「完整掃描沒掃到就修剪」的一般性對帳，只把借出與封存當例外。使用者回覆：「請先分析被移除有哪些情況……我想要解決的只有第三種，第二種應該被保留，第一種要看情況……理論上無法分辨第一種跟第二種，除非可以讀取到哪些書籍正在被借出」。設計因此整個改成只處理「書號變了」，#241 重新打開。issue 留言其實已經列出三個不能直接移除的原因，orchestrator 仍先提了刪除方案才被擋下。
- **U2**（中斷）：orchestrator 用前景模式（`run_in_background: false`）派修正 coder，使用者中斷了這次工具呼叫，之後回覆「繼續這兩項修正」。前景派工會讓使用者在 coder 跑完之前無法插話。
- **G1**：被中斷的 coder 留下半成品，但第一輪 coder 的輸出當時只有新檔案被暫存、修改過的檔案沒有暫存，兩批改動混在同一批檔案裡無法單獨還原。`SKILL.md` §3 規定「還原後重派」，實際只能改派 audit-and-complete。`code-cycle.md` Phase 3 步驟 2 已要求 verify 後暫存，orchestrator 是在暫存之前就派了下一個 coder。
- **G2**：Phase 1 沒看出的兩個設計缺口，都是前端 coder 回報才發現：讀不到伺服器書單時同步照常上傳（斷路器算到 0 本、擋不住），以及斷路器把沒掃到的封存書算進比例。orchestrator 在 Phase 1 讀過 `extension/src/sync/syncBooks.ts`，沒有檢查 `getPersonalBooks` 回傳 `{ error }` 的分支。
- **G3**：C1（同步結果在儲存途中套用時被舊清單蓋掉）來自 coder 把套用條件從 `status === "ready"` 放寬成 `status !== "loading"`。orchestrator 的 prompt 規定了套用後的三個狀態，沒有提「儲存請求在路上」這個時序；reviewer 的 prompt 有點名這一塊（引用 #246 的 4 個 CRITICAL），才抓到。
- **G4**：`origin/main` 中途合併 #247。Phase 4 開始前的基底檢查是乾淨的，到 Phase 5 才發現前進。當時所有改動只有暫存、沒有 commit，無法直接 rebase，最後用「暫時 WIP commit → rebase → `git reset --soft`」，並多派 coder、tester 各一次解衝突與調整上游新測試。流程文件只寫「rebase/ff」，沒有寫未 commit 狀態下怎麼做。
- **G5**：行數上限測試（`extension/tests/unit/eslintMaxLinesCeilings.test.ts`）要求上限等於實際行數。audit-and-complete 的 coder 因為 prompt 沒授權改設定檔，把 269 行的檔案留在上限 270，tester 的完整測試因此紅了一個，到 Fix Cycle 才修。
- **G6**：verify-before-test 的後端實測腳本試了三次才跑起來：`worker/` 沒有 `tsx`、`.ts` 被當成 CJS 不支援 top-level await，最後用 `extension/node_modules/.bin/tsx` 加 `.mts` 副檔名、從 `worker/` 目錄執行。
- **G7**：PowerShell 裡 `Set-Location worker` 會把後續呼叫的工作目錄留在 `worker/`，之後每個指令都要重新寫絕對路徑。

### 執行槓桿

- **E1**：派 agent 一律用背景模式，前景模式只留給「下一步立刻需要結果、而且幾秒內會回來」的情況。
- **E2**：讀同步或儲存流程時，對每個 API 呼叫都檢查「回傳 `{ error }` 而不是丟例外」的分支會走到哪裡；這次的 GET 失敗缺口是這樣漏掉的。
- **E3**：prompt 規定某個 effect 或 handler 的新行為時，一併列出它和其他非同步操作重疊的時序（這次是同步結果 × 進行中的儲存），不要只描述穩定狀態。
- **E4**：PowerShell 指令不用 `Set-Location` 進子目錄後留在那裡；需要子目錄時用 `pnpm --filter` 或在同一行結尾切回來。
