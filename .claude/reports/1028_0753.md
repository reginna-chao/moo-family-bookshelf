## 2. 卡點與摩擦

- **U1**（使用者，逐字）：「我當初建立 docker 相關檔案是為了避免專案可能過很久後回來要啟動環境無法啟動的保留手段，請問你還是覺得應該刪除嗎？」— 出現在決策關卡。我在分析階段把 Docker 檔案寫成「壞了、建議刪除」，依據只有讀檔推論（複製了不存在的 lockfile、漏 pwa／shared）。被反問後才實際 `docker build`，結果映像檔建得起來、三個 package 都建得出來、Worker 也起得來——「壞了」是錯的，正確診斷是「能用但靠運氣，且無人看守」。建議從刪除翻成修正加 CI 守門。根因：Phase 1 步驟 2 要求「執行例子」，但我對一個可執行的 artefact 只讀不跑就下了「刪除」的建議。
- **G1**（金魚 Round 1，16 條全 🟢）：草稿把 compose 的 `VITE_*` 值、audit job 要不要裝依賴、docker job 的實際指令與映像檔名、`changes.outputs` 的新欄位全部留給 coder「自己確認」。兩隻金魚各自查出同一批缺口（R2≈C2、R3≈C4、R1≈C5 重疊三組）。這些值在計畫階段全部查得到，事後補上花了一輪重審。
- **G2**（金魚 Round 2，6 條全 🟢，其中 D1 是隱私等級）：`.dockerignore` 的規則是根目錄錨定，`COPY . .` 會把 `worker/.dev.vars`、`.wrangler/` KV 狀態、`extension/.verify-selectors-profile/`（含讀墨登入狀態）烤進映像檔。Round 1 的 16 條都沒看到，是重審才抓到；而重審上限只有一次，若 Round 1 沒有改到「`COPY . .`」這個決定，這條不會被看到。
- **G3**（reviewer Round 1 S2 ＋ security-auditor INFO 1）：同一個 `.dockerignore` 缺口（`docs/resource/`）被 reviewer 和安全掃描各報一次；兩者並行派出所以沒有浪費等待，但兩份 prompt 都沒有告訴對方已在看什麼。
- **G4**（S3）：reviewer 聚焦審查以變異測試證明 `ciSuccessGate` 的 docker glob 清單漏 `package.json`，tester Round 2 在同一時段獨立發現漏 `.dockerignore`。兩個發現落在同一行清單，合併成一次 tester 派工；但 S4（reviewer Round 2 的「禁止 `!` 例外行」）晚了一輪才到，又多派一次 tester 與一次聚焦審查。
- **G5**（處方例外）：S4 的新增是 reviewer 處方逐字落地，共 7 行（含空行與一行註解），超過 code-cycle.md「≤ 5 行可由 orchestrator 自行核對」的門檻 2 行，多派了一次 reviewer（約 5 萬 token、69 秒）去確認一段 reviewer 自己寫的程式碼。
- **G6**（基礎設施）：reviewer Round 2 聚焦審查在 session 用量上限時以 429 中止；read-only，無殘留，續跑時重派即可。
- **G7**（coder prompt 預測錯誤）：我在 coder prompt 裡預告 `ciSuccessGate.test.ts` 會因新 job 而紅，實際上該檔的預期是下限與包含檢查，58 個全綠。沒有造成損失，但 coder 多花了解釋篇幅。

### Flow-structural

- **L1028_0753-1**：`target=.claude/skills/develop/references/code-cycle.md → Phase 1 步驟 2 | sketch=「建議刪除或宣告壞掉」的對象若是可執行的 artefact（Dockerfile、script、workflow job），分析階段必須實際跑過一次並記錄結果，不得只憑讀檔；跑不了的要標「未驗證」並把「它其實能用」列為替代分支 | status=proposed`（U1 的根因）
- **L1028_0753-2**：`target=.claude/skills/develop/references/code-cycle.md → Phase 1 步驟 8（執行計畫） | sketch=執行計畫對每個設定值（環境變數、埠、映像檔名、CI 步驟指令、job 的 needs/if）直接寫值，不得出現「coder 讀預設值後確認」；留給 coder 的只能是實作方式，不能是決定 | status=proposed`（G1：兩隻金魚 16 條裡 11 條是這一類）

### 執行槓桿（no flow gap）

- **E1**：reviewer 與 security-auditor 並行時，兩份 prompt 互相點名對方的 scope（「安全掃描負責 `.dockerignore` 與 secrets，你不必重複」），同一缺口就不會兩邊各寫一次（G3）。
- **E2**：聚焦審查要驗「只動了處方行」時，把 Round 1 暫存時的 blob id（`git rev-parse :path` 的輸出，在暫存當下記進 PLAN.md）直接寫進 prompt；這次 reviewer 自己用 `git fsck --unreachable` 找回來，可省一段工具時間。
- **E3**：單行、test-only 的 SUGGESTION（S3、S4 這一類）累積到審查結果全部回來再一次派 tester；這次 S3 與 S4 差一輪，多了一次 tester 與一次聚焦審查。
- **E4**：Docker 相關實測用 scratchpad 裡的 `FROM scratch` Dockerfile 加 `<name>.dockerignore` 對主 checkout 建 context，再 `docker create` ＋ `docker export | tar -t` 列檔——不建真正的映像檔、不動主 checkout，約 10 秒；記得 scratch 映像檔要有 `CMD` 才能 `docker create`。

## 4. Skill / Agent 增減建議

- **goldfish**：兩種 persona 在本 run 重疊 3 組（6 條），但各自獨有的發現（readiness 的檔案表、範圍引述；codebase 的 `host: true`、`basicSsl`、`rimraf` 掛載點）都只有一方抓到——保留兩種，不建議合併。
- **reviewer**：本 run 五次派工裡三次是聚焦審查（test 檔、修正回合、S4），每次 5 到 13 萬 token。採 L1028_0753-3 可少一次；其餘兩次是必要的。
- **tester**：四次派工中兩次（S3、S4）是兩行內的 test-only 修補，各約 9 萬 token；採 E3 可合成一次。
- 不建議新增 agent。
