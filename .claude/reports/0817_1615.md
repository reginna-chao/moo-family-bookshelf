## 2 卡點與摩擦

### U1 — verify-before-test 的手動驗證步驟在使用者環境中不可執行

> 「我沒有辦法測試 B，因為沒有另一個伺服器來建立新的家庭書櫃」

我在 gate 中把觸發條件描述成「端點 = 自訂」，使用者合理地把它讀成「需要第二台伺服器架一個新家庭」。實際條件是 `apiClient.getEndpoint() !== DEFAULT_API_ENDPOINT` —— 一個**建置期常數 vs 執行期儲存值**的比較，與家庭建在哪、有沒有第二台機器無關。

專案早就同時具備兩個端點（`.env.example` → `http://localhost:8787`、`.env.remote` → 已部署 dev worker），使用者原本的家庭就能直接用。這些資訊全在 `extension/src/constants.ts:22` 與根目錄 `.env*` 裡，**我在寫 gate 之前沒有讀**，事後才補讀並改寫成可執行的步驟。

代價：一次完整的使用者往返 + 一段本可避免的「你不需要第二台伺服器」更正。

### U2 — 給使用者的 console 指令沒有指明執行 context

> 「看起來會被卡住」（附 `Uncaught TypeError: Cannot read properties of undefined (reading 'local')` 截圖）

我給了 `chrome.storage.local.set({...})`，但沒說要在哪個 DevTools context 執行。使用者在頁面本身的 console（`top`，網頁 main world）執行，該處沒有 `chrome.storage`。

代價：第二次使用者往返。修法本身只有一行（切 context 下拉選單，或改用 Service Worker console）。

### G2 — 手動驗證的正向情境確認了，負向情境無法在真實環境確認

截圖確認了「自訂端點 → 顯示揭露」，但「預設端點 → 靜默」在該環境無法乾淨驗證（把端點改回預設後，家庭在 dev worker 上，請求會直接失敗，modal 根本不會開）。已由元件測試涵蓋並在報告中誠實標註，非缺陷，但值得記錄：**顯示層的「靜默」不變量天生難以手動驗證，設計 gate 時就該預期它只能靠測試守。**

## 3 改進提案

### Flow-structural

- **L0817_1615-1** — verify-before-test gate 的手動步驟必須「照著做就會動」：呈報前先確認 (a) 該狀態在使用者當前 build 中**可達**（讀 `.env*` / `constants.ts` 等建置期設定，別假設），(b) 每一條指令都指明**執行 context**（哪個 DevTools context、哪個 shell、哪個目錄）。`target=.claude/skills/develop/references/code-cycle.md`（Phase 3 step 3）| `sketch=gate 步驟需先驗可達性並標註執行 context` | `status=proposed`
- **L0817_1615-2** — 引入的新文案若與既有文案互為子字串／超字串，只有正向斷言的測試在 variant 被拿掉時仍會綠。本次 tester 自行察覺並改用完全相等 + 負向斷言，值得升成通則。`target=.claude/rules/test.md`（Anti-Drift Rules）| `sketch=子字串關係的文案變體需完全相等比對或負向斷言` | `status=proposed`
- **L0817_1615-3** — agent 寫進註解的**跨檔案事實斷言**（呼叫點清單、「還有沒有別處」、「能不能共用」）必須先實際查證再寫；查不動就別寫。本次一個 PR 內出現三次，且型別與測試皆攔不到。`target=.claude/agents/coder.md` + `.claude/agents/tester.md` | `sketch=註解中的跨檔案事實需先 grep 查證，未查證則不寫` | `status=proposed`

### 執行槓桿（no flow gap）

- **E0817_1615-1** — 派 tester 前自己先跑一次受影響的測試檔，把紅燈清單（含 `file:line` 與實際 vs 期望字串）寫進 prompt。本次省掉 tester 的探索回合，且 coder 預測的紅燈與實測完全吻合，順帶驗證了 coder 的自我回報可信。
