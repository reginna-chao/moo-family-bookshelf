## 2. 卡點與摩擦

- **U1**（開場）：「仍要現在做」。Issue 自訂的 90 天等待被使用者否決。分析階段把後果寫成「所有裝置重新登入一次」，但漏了一種帳號救不回來（見 G1）。
- **U2**（阻擋項決策後）：「我先跟你說一下目前實際狀況……token: 跟 auth: 開頭的只有各兩筆 這樣會影響計畫嗎?」。使用者主動提供正式 KV 實況，計畫從「寫一次性遷移腳本」（C）反轉成「接受一次重新登入」（B′）。在此之前我問的是「官方站大約幾台裝置」這種估計值（答「50 台以下」），而不是可以直接數出來的 key 數（實際 2）。
- **G1**（P0 在 GO 之後才浮現）：coder 做完 W1 才指出驗證碼（`code`）帳號上線後會被永久鎖住——復原加入要驗證碼，驗證碼只能用受保護的 `POST /api/user/:id/verify/otp` 產生，沒有 token 就產生不了。分析階段寫「客戶端的 401 → 復原加入路徑會自動接手」時只追了 PWA／Extension 的程式路徑，沒有按驗證方式（none／pin／pattern／code）逐一走一遍；三隻金魚看的是計畫，計畫斷言了這個前提，所以也沒抓到。`docs/secret-token-storage-plan.md` §4 第 1 點其實早就寫著 #425 為此才不硬切。
- **G2**（白跑的金魚）：選 C 後我立刻把修訂 v2（腳本 W3／W4）派給 implementation-readiness 重審；使用者隨後給了 U2 的實況，腳本撤銷，那次派工（約 150k token，已中止）沒有產出。順序錯了：新計畫依賴的事實（正式 KV 規模）應該在重派之前先問。
- **G3**（金魚 Round 1 的真問題）：24 個發現全部成立，其中 IR-G4／CD-G2／DC-G1 同時指出我設計的「明文 Bearer 打 refresh 回 401 且無寫入」在中介層就被擋、永遠到不了 `renewPresentedAuthToken`，是恆真的假檢查；真正改變的行為（hash 通過＋舊形狀 `auth:` → 空窗鑄新）沒有驗收。Round 2 又抓到 13 個（未使用 import、`seedAuthToken` 寫兩半、`writeTrail()` 不記讀取），全部成立。
- **G4**（coder／tester 分工與 typecheck）：`worker/tsconfig.json` 的 `include` 含 `tests/**`，coder 不碰測試，所以 W1 回來時 `pnpm typecheck` 必紅。金魚 IR-G7 要求計畫寫明關卡判定（「只允許列舉的測試檔紅，`src/` 任何錯誤都是 coder 缺陷」），照做後關卡沒有爭議。
