## 2. 卡點與摩擦

- **U#：無。** 四個決策、金魚選項、GO、驗證關卡、commit 關卡，使用者全部採用建議，沒有一次改寫計畫。
- **G1：金魚 Round 1 找到 12 項、Round 2 又 7 項，全部 🟢。** 證據：PLAN.md `## 金魚審查`。Round 1 的 I1、I3、I4、I5 全是「介面沒寫出來」「抽哪一塊沒指名」——計畫草稿把這些留給 coder，不是金魚挑剔，是草稿寫得太粗。Round 2 的 R-G1（hook 依賴漏 `authRef`，`exhaustive-deps` 是 error 會讓 lint 紅）是真正值回票價的一項，其餘六項是精確度修正。
- **G2：三個目標檔都卡在行數上限（370／574／258 = 上限）。** 證據：`pwa/eslint.config.js` 差異。每加一行都要抽一塊，計畫得先指名抽哪一塊（I3、I4），抽出的 `transport.ts`、`authStorage.ts`、`useRecoveryJoin.ts` 讓三個檔案分別減到 316／525／148。這是這個 repo 的常態，不是這次特有。
- **G3：orchestrator 自己的 shell 摩擦。** `node -e` 的 JS 字串含反引號，被 bash 當成指令替換吃掉（PLAN.md 追加失敗一次，改用 Edit 工具）。同類教訓已在 memory（`project_bash_sandbox_quirks`），這次仍踩到。
- **G4：tester 是牆鐘瓶頸（28 分鐘）。** 其中 mutation 探針（把每條防護拿掉確認測試變紅）占大頭；測試檔聚焦審查又獨立做了一次同樣的 13 組探針（21 分鐘）。兩次探針結論一致，第二次是重複工。
- **G5：PR 開出後，外部 Codex 審查找到一項必修，流程內三個審查都放過了。** `adoptRefreshed` 只比對本分頁記憶體裡的 session（`isLiveSession` 對 localStorage 只看 userId）：另一分頁換 PIN 存下新 token 後，本分頁較早送出的續期回應會把舊 token 寫回去，重新載入就被要求重新驗證。證據：修正 commit `371cca30`、跨分頁回歸測試三個案例。流程內的位置：Phase 1 風險清單寫了「多分頁同時續期 → 接受：Worker 等冪」，只想到兩個分頁續「同一顆」token，沒想到另一分頁會「換」token；security-auditor 的報告明確寫出這個競態，卻標為「跟 `useRecoveryJoin`／`useRotatedTokenPersistence` 原本就有的模式一樣、極窄」而放行；reviewer 的 12 個探針沒有跨分頁情境。三道關卡都看到了「另一分頁」卻沒有人把它分級——依 change-triage 它能寫出會紅的測試（Codex 就寫了），是 P1，不是殘餘。
