## 2. 卡點與摩擦

- **G1 「預期會紅的測試」列錯（金魚 Round 1，Blocker）。** 計畫列了兩個斷言 `console.error` 沒被呼叫的檔案，但它們的 env 一律帶 `DEV_MODE`，新程式在那條路徑直接回 `off`，不會多出 log；真正會紅的是 prod-mode 下用 `toEqual` 比對完整 log 清單的案例（`worker/tests/integration/verifyAttemptCeiling.test.ts`、`userDeleteMarkRetry.test.ts`）。我只 grep 了「斷言沒有 log」，沒看 env 工廠。
- **G2 驗收「coder 交出時 `pnpm test` 全綠」不成立（金魚 Round 2，Blocker）。** 同一個原因：在共用路徑新增一行 log，既有的完整 log 斷言一定會紅，而 coder 不能改測試。最後改成照流程，coder 只驗 typecheck／lint／build，全綠留到 tester 之後。
- **G3 執行時 API 是否可用留給「之後的演練」決定（金魚 Round 1）。** 計畫寫「若演練顯示 compatibility date 下沒有 `ctx.storage.kv` 就改用 sql」，金魚指出 tester 的假 storage 會因此對不上。用 Miniflare 寫一支約 30 行的探針，一分鐘就確認可用、50 個並行恰好放行 10 個，應該在分析階段就做。
- **G4 計費假設寫成「看起來不計費」（金魚 Round 1、2 各一次）。** duration 的計費方式第一次只查了價格頁，第二次才找到生命週期文件和「idle and eligible for hibernation are not billed」的原句。
- **G5 upstream 在 run 中前進三次。** 兩次和本 run 的文件（`CHANGELOG.md`、`docs/architecture.md`、`.claude/rules/backend.md`）重疊，各做一次 WIP commit + rebase，其中一次有目錄樹衝突（兩行並列，機械合併）。
- **G6 coder 不能碰測試樹，但 vitest 需要 `cloudflare:workers` 的 alias。** stub 只好放在 `worker/vitest/`，連帶要改 `tsconfig.json` 的 include 和 `package.json` 的 lint 路徑（金魚 Round 2 才發現 stub 不在檢查範圍內）。
- **G7 審查發現 alarm 失敗會改變 `reserve` 的回答（reviewer 逐項判定第 11 項）。** 計畫的探測表只寫「下一次補設」，沒寫「這次 RPC 會 reject」。多一輪 coder＋tester＋重審。

## 4. Skill / Agent 增減建議

- 金魚兩輪約 75 萬 token，是這次最大的消耗；兩輪各抓到一個 Blocker（G1、G2），兩個都是「測試會怎麼紅」的誤判。若 L1 被採用，這兩個在自檢時就能擋下。
