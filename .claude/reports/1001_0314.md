## 2. 卡點與摩擦

- **U1**（使用者，看完 KV 腳本輸出）：「沒有檢查到重複書名? 但實際上使用者在讀墨的介面上只有五百多本」。issue 寫的判斷依據（`readmooUrl` 指向 `mooink.readmoo.com`）在正式資料裡一筆都沒有；實際特徵是 `bookId` 只有 7～8 位。第一輪 coder 的產出整個作廢。證據：備份檔統計 703 本 = 266 本 15 位 + 437 本 7～8 位，網址全是 `readmoo.com`。
- **U2**（使用者，第一次 verify-before-test 關卡）：直接關掉 AskUserQuestion 沒回答。原因是當時他正在做 KV 備份，關卡問題和他手上的事無關。之後靠 U1 的資料才推進。
- **G1**：Round 1 reviewer 抓到 C1（PATCH 清不掉伺服器上的舊書目）、tester 抓到 C2（快取讓已取消的分享復活）。兩個都是「本機清單少了伺服器有的書」這件事和 `decideSaveStrategy` / `reconcileBaseline` 的既有假設衝突，coder 第一輪沒有想到。
- **G2**：C1 的修法（強制 PUT）被安全掃描判為 WARNING（送出載入時快照，會蓋掉別台裝置）；使用者選改 PATCH 方案後，reviewer 與 security-auditor 各自獨立抓到 C3（搬過去的分享狀態沒隨 PATCH 送出），修完再抓到 C4（PWA 真值正規化 vs 嚴格快照比對）。同一個「PATCH 該送什麼」問題連續三輪才收斂。
- **G3**：worktree 分支在 run 中被切成 `claude/issue-235-052c30`（另一個 session 在同一個 worktree 開工），staged 修改沒丟但分支名錯了。到使用者截圖才發現。
- **G4**：coder 兩度誤把 `\d{12,}` 的判斷寫成「scraper 不產生短 id」，reviewer 指出只有 `.privacy` 備援路徑有這個 guard；不影響結果但註解措辭被改了兩次。
- **G5**：`usePersonalBooks.ts` 頂在 max-lines 上限（306 → 303），每一輪 coder 都要花力氣在同檔省行數；有一次 coder 想合併兩個 `storage.local.set` 呼叫，發現會弄壞既有斷言才改走別的路。

### 執行槓桿

- **E1**：正式 KV 手動修資料時，指令只給 Git Bash 版本並明說原因（PowerShell 的 `>` 會把中文書名存壞），並在腳本裡偵測 UTF-16 BOM 直接拒收——這次有做，下次直接沿用。
- **E2**：修 PATCH/PUT 決策時，第一輪 coder prompt 就附上「三種書：dirty / 被搬移旗標的非 dirty / 本機沒有的伺服器書」的表格，讓 coder 一次考慮完整，而不是靠三輪 review 補齊。
- **E3**：被 pin 在 max-lines 上限的檔案要動時，先在 prompt 裡點名可以省的行（過期註解、重複 clearTimeout），省得 coder 每輪自己找。
