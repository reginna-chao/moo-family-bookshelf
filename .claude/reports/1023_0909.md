## 2. 卡點與摩擦

- **G1**：frontend coder 的派工指示寫「每新增一行要在同檔刪一行，可縮短附近註解來抵銷」，但 `.claude/rules/frontend.md` → Coding Conventions 明文禁止「squeeze a file under its cap by compressing comments」。`pwa/src/api/client.ts` 當時正好 615 行等於上限，coder 依規則優先停下回報 blocker，多一輪 coder（把 `readEnvelope` 拆到 `pwa/src/api/envelope.ts`）。SKILL.md §3 已要求「state the file's headroom」，但 headroom 為 0 時沒有說該怎麼辦，orchestrator 便給了違規的指示。
- **G2**：run 在兩位 coder 回報後、拆檔派工前，被使用額度上限切斷。把待辦（拆檔決定、之後的流程、預期變紅的測試清單）寫進 `.claude/runs/<slug>/PLAN.md` 後停下；下一段 session 讀 PLAN.md 直接接續，沒有重新規劃。Phase 0a step 3 的設計目的第一次被實際用到，有效。
- **G3**：worktree 是新開的，沒有 gitignored 的 `worker/.dev.vars`；本機 curl 驗證前從主 checkout 複製一份。Phase 3 的 gate 說明已提到要檢查，這次在 coder 回報前就處理掉，沒有卡到關卡。
- 無 U#：使用者三個決策題與 GO 都選推薦項，無修正。

## 3. 改進提案

### Flow-structural

- **L1023_0909-1**：`target=.claude/skills/develop/SKILL.md | sketch=§3 的 MAX_LINES_LEGACY_CEILINGS 段：headroom 為 0 或不足時，coder prompt 必須指名要拆出的區塊與新檔名（split），並明寫禁止壓縮註解；不要把「怎麼擠回上限」留給 coder 判斷 | status=proposed`。證據：G1，多一輪 coder。
- 不提升：G2 的 PLAN.md 接續流程照規則跑就順；G3 已在 Phase 3 gate 說明內。

### 執行槓桿

- **E1**：派 coder 前先 `wc -l` 目標檔並對照 `eslint.config.js`；等於上限的檔案，在規劃階段就選好拆出的區塊（這次 `readEnvelope` + `NO_CONTENT_STATUS` 共 11 行，淨省 10 行），寫進第一次派工（G1）。
- **E2**：backend 的 verify-before-test gate 由 orchestrator 用 curl 實測效果好：coder 還在跑時就把腳本寫好放 scratchpad（建立家庭取 token → 標記 → 公開 GET → 新端點三種 token 情境），coder 一回報就能跑，使用者看到的是實測結果而不是「請你自己 curl」。
- **E3**：production 一 stage 就把 tester ×2、reviewer ×2、security-auditor 五路同時派出（reviewer 讀 index），之後只剩測試檔的聚焦審查要串行。這次審查與測試總時間約等於最慢的一路，維持這個做法。
- **E4**：每個關卡的答案當場寫進 PLAN.md `## 決定`，額度或 session 中斷時下一段不用猜（G2）。
