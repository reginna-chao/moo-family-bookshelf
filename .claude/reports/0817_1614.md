## 2 卡點與摩擦

**U#（使用者更正）：無。** 使用者 5 次介入全為決策回覆（4× AskUserQuestion + 1× 「行為正確，繼續」），零更正、零打斷。需求分析與驗證關卡都一次通過。

**G1 — 錯誤範例從任務描述一路寫進安全規格文件（最嚴重）**
任務描述舉例 `moo-a-b@http://192.168.1` 為 invalid 中間態。orchestrator 未驗證即轉寫進 coder prompt → 進入 `shared/src/api/syncCodeHost.ts` 的 JSDoc → 再被 S2 帶進 `docs/architecture.md` §六的安全控制規格。實際上 WHATWG 會展開簡寫 IPv4（`192.168.1` → host `192.168.0.1`），命中私網白名單而判定 **valid**。
加重情節：orchestrator 在 Phase 4 已自行以 node 實測發現此事並向使用者回報，**卻只當成「事實更正」敘述，沒有排進修復**；兩輪後由 reviewer 以 CRITICAL 抓回。

**G2 — 新增的一致性測試被 CI 路徑過濾架空**
S5 的 parity 測試只放在 extension 套件。`.github/workflows/cicd.yml:30-42` 的 `extension` filter 僅含 `extension/**`/`shared/**`，故**只改 PWA hook 的 PR 永遠不會執行它** —— 正是該測試自述要防的漂移方向。tester 在交付時自行於 Open Questions 標示「reviewer 可能會 push back 的唯一一點」，orchestrator 未處置，由 re-review 提出具體 CI 證據後才補（S-1）。

**G3 — PWA 預填不對稱在需求階段可預見卻漏掉**
orchestrator 設計了 settle trigger 4（首次渲染非空即定案），但未檢查 PWA 的 `syncCodeInput` 是 `useState("")` + effect 灌入，導致邀請連結預填仍走 600ms。tester 寫測試時才發現並記入 Open Questions，成為 review S3，第 1 輪修掉。

**G4 — base reviewer 被 skill 流程強制序列化**
production code 在 verify-before-test gate 後即凍結，base reviewer 與 base tester 檔案互斥、無資料相依，卻因 `code-cycle.md` Phase 4 的 gate 條件（「tester done」）而序列執行，白付約 692s wall-clock。

## 3 改進提案

### Flow-structural

- **L0817_1614-1** — 使用者請求中的具體範例（URL / payload / id / 錯誤字串）在轉寫進 agent prompt 或文件前必須先實測驗證；未驗證者標記為待證而非當成事實敘述。
  `target=.claude/skills/develop/references/code-cycle.md | sketch=Phase 1 加一條：quoted concrete examples are unverified input — execute them before they enter a prompt or a doc | status=proposed`

- **L0817_1614-2** — orchestrator 自行發現的缺陷必須進 Fix Cycle Log 並取得處置（修 / 接受 / 跳過），不得只在回覆中敘述。G1 的根因不是沒發現，是發現後沒有承載機制。
  `target=.claude/skills/develop/references/code-cycle.md | sketch=Fix Cycle Log 增列 orchestrator-discovered 來源，與 reviewer findings 同等處置 | status=proposed`

- **L0817_1614-3** — 新增跨套件／一致性測試時，必須對照 CI 路徑過濾確認「它所防的那種變更會觸發它」；只在單邊執行的守門測試比沒有更糟，因為它宣告了做不到的保證。
  `target=.claude/rules/test.md | sketch=Anti-Drift Rules 增一條 CI-reachability check（含 cicd.yml filter 對照） | status=proposed`

- **L0817_1614-4** — verify-before-test gate 通過後 production code 已凍結，reviewer 可與 tester 平行派送。
  `target=.claude/skills/develop/references/code-cycle.md | sketch=Phase 4 gate 條件放寬為「coder done + 使用者確認」，tester 與 reviewer 平行；test-code findings 待 tester 回來再併 | status=proposed`
  _Cut-before-add_：此為既有 gate 條件的改寫，非淨增行。

### 執行槓桿（E#，無流程缺口）

- **E1** — subagent 回報的 Open Questions 若指出它自己選擇不處理的風險，視同 finding，該階段收尾前必須處置。本 run 中 S3 與 S-1 都被 tester 預告過，各多花一輪。
- **E2** — 雙生檔案／雙 App 任務，在需求階段就把 CI path filter 列進限制清單，與「行為必須一致」的要求並列。
- **E3** — 派送 agent 前先跑一次「我引用的事實有哪些是我沒驗過的」自檢；本 run 唯一的 CRITICAL 完全源於此。

## 4 Skill / Agent 增減建議

- **不新增任何 agent。** 現有 coder / tester / reviewer / security-auditor 分工在本 run 完整發揮：reviewer 兩度抓到 orchestrator 的疏漏（C-1、S-1），security-auditor 未採信 orchestrator 的描述而自行列舉兩端所有 endpoint 採用點，得出「顯示層 invalid 集合與客戶端拒絕集合是同一個函式」這個決定性結論。
- **reviewer 的事實查證行為值得固化。** 它對文件中的具體範例實際執行 URL 解析器來反證，這正是抓到 C-1 的動作。建議 `/distill` 時考慮在 `.claude/agents/reviewer.md` 明確賦予「文件與註解中的具體範例需實測」的職責 —— 目前是該 agent 自發行為，非契約。
- **無可精簡項。** 本 run 未出現冗餘 skill 載入；`/develop` 的 §0 intent fork 一次命中 CODE 路徑。
