## 2. 卡點與摩擦

使用者糾正（U#）：沒有。使用者在 16 個選擇題裡有 1 題沒選建議選項（補空規則選「第一個打開的擴充功能上傳」），屬於決定，不是糾正。

- **G1：推薦的選項，前提沒先查。** 決策關卡第 7 題把「選項頁直接送伺服器」列為建議，並註明前提未驗證。決策之後的規劃代理才查出兩件事：`ApiClient` 在 401 時會刪本機 token（`extension/src/api/auth-refresh.ts:216-217`），Worker 的 CORS 不放行 `moz-extension://`（`worker/src/index.ts:64`）。兩者都是一次 grep 就查得到的事實。結果多一輪補問，使用者改選另一個選項。
- **G2：決定的後果在決策之後才浮現。** 補空規則（第 1 題）問完之後，規劃代理才指出四個 key 存在瀏覽器上、不分帳號，以及「連沒動過的項目也上傳預設值」會蓋掉別的瀏覽器的設定。又補問一題。根因和 G1 相同：深入調查（Plan 代理）排在決策關卡之後。
- **G3：金魚 Round 2 的修正帶出新缺陷，重審上限擋不到。** 套用 R3 時把「`save` 成功後清標記」的規則寫成「只清值等於送出值的欄位」，和同一份計畫併發表裡「`save` 先成功並清掉標記」矛盾。Round 2 已是唯一一次重審，沒有下一隻金魚。缺陷一路進了 production，在 review 階段才被前端 reviewer 與前端 tester 各自用實測抓到（C1）。#425 的 run 出現過同一類情況。
- **G4：平行的唯讀代理在 scratchpad 互相撞到。** 兩個 reviewer 都用 `scratchpad/probe/` 與同名的 `vitest.probe.config.ts`，其中一個回報設定檔可能被對方短暫蓋掉。派工 prompt 沒有指定各自的暫存子資料夾。
- **G5：shell 引號在 worktree 留下空檔。** 主 session 的 `node -e "setTimeout(()=>{},1500)"` 留下一個名為 `{}` 的 0 byte 檔；一個 reviewer 的 `node -e` 留下 `worker/console.log('ok'))`。兩者都靠事後的 `git status` 才發現並刪掉，沒有進 commit。
- **G6：tester 在跑的時候 production 還在動。** 前端 tester 執行期間，文案 coder 與 C1 的 coder 先後改了 production 並被 stage。兩個 tester 都在回報開頭註明「staged diff 的 hash 變了」並自行確認影響範圍。這次沒出錯，但「production 凍結後才平行派 tester」的前提實際上不成立。
- **G7：Explore 與 Plan 重複讀同一批檔案。** Explore 的盤點（23 萬 token）沒有交給後來的 Plan 代理（31 萬 token），Plan 又把四項設定的讀寫點重讀一次。
- **G8：金魚的發現全文輸出兩次。** 流程要求表格「原文照抄」。21 項發現先寫進 `PLAN.md`，再原樣貼到對話，主 session 光這一步就輸出兩份長表。

沒有摩擦、值得留著的做法：

- 兩個 client 的行數上限都是零餘裕，用「一個欄位＋shared 的 `accountSettingsApi`」只加 7 行，再各做一個小拆分就過了。
- 兩個 tester 與兩個測試 reviewer 都附了變異證據，TS1 就是這樣找到的。
- 後端的實測由 orchestrator 用本機 Worker 加拋棄式帳號跑完，手動驗證關卡只剩前端要使用者看。

## 4. Skill／Agent 增減建議

- **不增不減 agent。** 這次每一類代理都抓到別人沒抓到的東西：goldfish design-critic 抓到 KV 每秒一次與 gate 時機，前端 reviewer 抓到 C1，測試 reviewer 抓到 TS1。
- **goldfish 的 `implementation-readiness` 與 `codebase-details` 有重疊**：I6／C2（versionFetch 的 twin）、I7／C3（重複的 helper）各報了一次。兩隻合計 36 萬 token。可以考慮讓 `codebase-details` 專管「和現有程式碼矛盾」，`implementation-readiness` 專管「計畫沒寫死」，在 persona 定義裡寫清楚邊界。
- **測試檔的 focused review 值得留**，但可以瘦身：tester 已附變異證據的案例，reviewer 只需要抽查「斷言有沒有被放寬」與「假伺服器是否和真的一致」，不必重跑全部變異。
