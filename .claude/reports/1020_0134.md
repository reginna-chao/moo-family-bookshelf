## 2. 卡點與摩擦

### U#（使用者修正）

無。三個關卡（GO、驗證、C1 修法）都採用建議選項。

### G#（關卡重試、失敗驗證、返工）

- **G1 同一個根因造成兩輪 P0。** 第一輪 coder 回報時把「被略過的新書與已存舊書同名」判為不可能（「X 書名超過上限代表 O 的書名也超過上限」），但超過上限的欄位可以是作者或分類，書名仍然相同。security-auditor 抓到修剪路徑（`extension/src/sync/pruneBooks.ts`），reviewer 抓到改名與舊 id 配對（`renamedBooks.ts`、`legacyBooks.ts`）；修完後第二輪 reviewer 再抓到個人書櫃載入時的舊 id 解析（`extension/src/dialog/usePersonalBooks.ts:75`）沒有爬取結果可參考。根因只有一個：從合併清單拿掉一筆資料，下游所有「同名／同 id 比對」都看不到它，而這些比對分散在四個模組加一條載入路徑。需求分析時沒有把「清單少一筆」的消費者列出來。
- **G2 前提錯誤：「伺服器上的值已在上限內」。** Plan agent 與我都採用這個前提，但 #327 的上限還沒打 tag，正式 Worker 到打 tag 前仍會收超長資料，自架 Worker 也可能有舊資料。兩位 reviewer 同時判 CRITICAL，使用者決定改 Worker 放行相同原值，多出一輪 backend coder + tester + 重審。`git tag --contains 946b7fe` 是空的，一個指令就能避免這個前提。
- **G3 reviewer 誤跑整套測試。** frontend reviewer 用 `mergeConfig` 疊在套件設定上做探針，`include` 陣列合併後跑了全部 5149 個測試，與 tester 同時間執行。這次沒有出現 flake，但這是已知的 CPU 競爭來源。
- **G4 coder 執行了 `git add -N`。** 指示說不碰 git 狀態，coder 為了查行尾還是做了 intent-to-add。無害，staging 時覆蓋掉。
- **G5 Round 2 文案改動多一次派工。** 第二輪修法改變了讀者看得到的行為（同名新書也不加進書櫃），但 CHANGELOG 的 owner 是第一輪 coder，第二輪 coder 不能碰，於是多派一個只改一行的 coder。
- **G6 onboarding 的防護測試在變異下不會紅。** tester 自己回報：onboarding 本來就走 `holdBackRenameCandidates`，同名新書早就被延後，所以新案例分辨不出這次的規則。保留為回歸測試，但不是這條規則的證據。
