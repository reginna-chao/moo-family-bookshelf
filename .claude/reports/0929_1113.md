## 2. 卡點與摩擦

- **G1：平行派出兩個 coder，而且其中一個的產物會約束另一個。** 行數上限的清單不能包含另一個 coder 正在拆的檔案，拆出來的新檔也必須不超過 200 行。兩份 prompt 都寫明對方負責哪些檔案、自己 lint 時會看到哪些「預期中的錯誤」，所以沒有互相踩到。這是 SKILL.md §3「平行 prompt 要寫出 sibling 的檔案」做對的例子，不需要提案。
- **G2：tester 做 mutation check 時暫時改動 ESLint 設定，reviewer 同時在審。** 這次在 reviewer 的 prompt 裡要求它一律讀 index（`git show :<path>`），不讀工作目錄，所以沒有重演 0924_1831 報告 G2 的狀況。這是 L0924_1831-2 的佐證：同一個問題第二次出現，而這次靠 prompt 裡的一句話就避開了。
- **G3：上一個 run 收尾時，`sync_with_base_branch` 在 fetch 就失敗。** 上游沒有動到受保護路徑，所以改成自己跑 `git merge`。當時本機的 `git fetch` 是成功的，可能是 host 端的網路或認證問題。之後又遇到一次 SSH push 被重設，重試就成功了。
- **G4：ESLint 用 stdin 做 mutation check 時不能用虛構的檔名。** 因為 lint 是 type-aware，不在 tsconfig project 裡的檔名會變成 parsing error，所以 coder 改借用一個既有、沒列在清單裡的小檔名。
- **G5：Write 工具會把字串裡的 `\r`、`﻿` 這類跳脫序列寫成真正的控制字元。** tester 發現後，改成在測試裡用 `String.fromCharCode` 組出這些字元。
- **G6：開發工具的套件漏洞（vitest、web-ext、miniflare 的相依套件）連續兩次在安全掃描裡以 INFO 出現。** 依 change-triage 屬於 P2，兩次都沒有處理；但每次掃描都會再報一次，形成固定雜訊。

## 3. 改進提案

### Flow-structural（L#）

- **L0929_1113-1**：`target=.claude/skills/develop/references/code-cycle.md | sketch=Phase 3 step 4 平行派 reviewer 時，prompt 固定加一句「production 和設定檔一律讀 index（git show :<path>），不讀工作目錄」。這次 G2 證實一句話就足夠，可以和 L0924_1831-2 合併採納 | status=proposed`
- **L0929_1113-2**：`target=.claude/rules/test.md | sketch=Anti-Drift Rules 補一條：測試需要 CR、BOM 等控制字元時，用 String.fromCharCode 或 \\u 跳脫在執行期組出來，不要讓檔案裡出現真正的控制字元（編輯工具可能會把跳脫序列解碼成字元） | status=proposed`

### 執行槓桿（E#）

- **E1**：對 type-aware 的 ESLint 做 stdin mutation check 時，`--stdin-filename` 要借用 tsconfig project 裡已有的檔名。
- **E2**：開發工具的漏洞既然每次掃描都會出現，可以在下一次處理相依套件時一起升級（vitest ≥ 3.2.6、web-ext、`@cloudflare/vitest-pool-workers`），讓掃描結果不再有這條固定雜訊。這不是這次 run 的範圍。
- **E3**：修正註解這種小改動，可以和 reviewer 平行跑，只要讓 reviewer 讀 index 就好。這次讓 reviewer 等了約 160 秒，其實不需要。

## 4. Skill / Agent 增減建議

- 不增不減。這次 coder 自己用 TypeScript 編譯器 API 寫比對腳本，證明 callback 內容和 hook 順序完全相同；reviewer 也用 `diff -w` 從兩個方向複核。對搬移型重構來說，這種「機械式等價證明」比人工閱讀可靠，值得保留成習慣。
