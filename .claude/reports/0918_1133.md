## 2. 卡點與摩擦

**U（使用者修正）**：無。三次 AskUserQuestion 皆選建議選項。

**G1（測試檔算一個 area → `full` scan，第三次）**：`cicd.yml`（config）+ `worker/tests/…`（worker）= 2 areas。
auditor 自陳 Dim 3–6、8 無受測面。與 `0917_1601.md` G4、L0917_1601-3 同一件事，第三次出現。

**G2（沒有 `config` scope，第三次）**：三個 agent prompt 又各自手寫 scope 免責。L0917_1601-1、
L0918_0957-1 已兩次提出，本報告第三次。

**G3（頂層 `permissions:` 會把 paths-filter 打壞，靠事前預判擋下）**：頂層 `contents: read` 讓其他權限
歸零，`dorny/paths-filter` 在 `pull_request` 走 REST API 需要 `pull-requests: read`。我在 brief 裡要求 coder
讀 action README 查證再補；auditor 後來確認「repo 預設改唯讀後，沒這行 PR 上的 `changes` 會直接失敗」。
**權限硬化的必要前置是逐 action 的權限需求盤點**，不能只看 job 自己跑什麼。

**G4（issue #196 的範圍寫錯了一半）**：issue 依第一次 auditor 的 remediation 寫「五個 check job 加
`persist-credentials: false`」。這次 auditor 做了逐 job 有效權限表才發現：六個 CI job 的 token 在 repo 預設
改唯讀後只值 `contents: read`，真正持有 `contents: write` 又緊接著跑建置工具鏈的是兩個 release job，
它們反而沒在清單裡。我判定為 #196 意圖的另一半併入，並推廣成「全檔每個 checkout」讓規則普遍化。
**教訓：寫 token 相關 issue 時，先列「每個 job 的有效權限 × 是否執行不受信任程式碼」的表，再決定範圍。**

**G5（修 S-1 引出 S-2：regex 型 guard 的拼寫盲點）**：S-1 把「只看第一個 checkout」改成全部切片；
R2 reviewer 立刻示範 `- name: Checkout` + 次行 `uses:` 的寫法讓 `checkoutSteps` 抓不到，該 job 靜默退出規則，
`>= 13` 下限仍過。修法是「原始出現次數 vs 解析切片數」的交叉檢查。**這是 regex tripwire 的通用弱點：解析器
看不見的合法拼寫 = 靜默漏檢；每個切片型 helper 都該配一個粗略計數的 companion。**

**G6（環境小坑 ×2）**：tester 的 shell 裡 `npx eslint` exit 127（PATH），改 `./node_modules/.bin/eslint`
即過；`npx actionlint@latest` 無 bin（Go binary），以 prettier parse + tripwire 替代。

**G7（契約式平行派工，效果好，記為正面證據）**：coder 與 tester 拿同一份「yml 最終形狀契約」平行開工，
tester 用 seam 對 scratch 副本做 mutation，真檔在 coder 落地後自然轉綠。R1、R2 各省一段序列等待。
