## 2. 卡點與摩擦

- **U1**（需求確認）：使用者在「抓不到時」這題沒有選，而是反問：「為什麼推薦照常放行？是可以繼續看到家庭書櫃嗎？」。選項說明寫的是機制（「視為無法確認，維持現有行為」），沒有寫使用者會看到什麼、推薦的理由是什麼。補了說明並加一個折衷選項後才定案，最後選的正是那個折衷選項。
- **U2**（verify-before-test gate）：使用者問：「哪一個 worktree」。gate 的說明只寫「在 worktree 根目錄建置」「來源指到這個 worktree 的 `extension/dist`」，沒有給絕對路徑。`code-cycle.md` Phase 3 第 3 步已要求「in a worktree, the worktree path」，是 orchestrator 沒照做。
- **G1**（推薦理由未查證）：推薦「每次頁面載入檢查一次」時寫了「換帳號都會重新載入頁面，所以涵蓋得到」。這是對讀墨行為的推測，沒有標成未查證。安全掃描指出多分頁情境下不成立，最後開成 #277。使用者是依這句話選的。
- **G2**（CHANGELOG 連續衝突）：兩次 rebase 都只有 `CHANGELOG.md` 衝突。每個 run 都把 bullet 加在 `### 問題修正` 的最後一行，平行的 session 一定撞在同一行。兩次都要先做 `wip:` commit 才能 rebase，commit gate 再合併。
- **G3**（`gh` 首次呼叫失敗）：第一次把 `settings.local.json` 的整份內容塞進 `GH_CONFIG_DIR`，指令失敗；改成直接寫路徑後成功。
- **G4**（S1 是實作引入的退化）：開機流程從「只讀 storage」變成「等 1.5 秒」，coder prompt 的 R1 沒有提醒「期間其他會改 view 的事件要優先」。reviewer 抓到，多一輪 coder → tester → 重審。
- **G5**（手動驗證早於 S1 修正）：使用者確認的是 S1 修正前的版本，修正後沒有再實測，只在最終報告揭露。

## 3. 改進提案

### Flow-structural

- **L1005_1540-1**：`target=.claude/skills/develop/references/code-cycle.md | sketch=Phase 1 step 2 的「cited specifics are leads, not facts」也適用於 orchestrator 自己寫進選項說明或推薦理由的外部行為假設（第三方網站怎麼運作）；未查證就標「未查證」，並說明假設不成立時的後果 | status=proposed`
- **L1005_1540-2**：`target=.gitattributes（或 .claude/rules/user-facing-copy.md 的 "Where a change is recorded"） | sketch=CHANGELOG.md 設 merge=union，或規定 bullet 插在該小節最前面而不是最後一行，讓平行 run 不再固定衝突 | status=proposed`
- **L1005_1540-3**：`target=.claude/skills/develop/references/code-cycle.md | sketch=Phase 1 風險清單加一項：把同步的開機／掛載流程改成非同步等待時，列出等待期間可能改變 view 或身分的事件，寫進 coder prompt | status=proposed`
- U2：`不提升：規則已存在（Phase 3 第 3 步要求寫出 worktree 路徑），屬執行疏失，見 E1。`
- G5：`不提升：單次情況；Fix Cycle 的修正有回歸測試與重審，是否再實測由使用者在 commit gate 決定。`

### 執行槓桿

- **E1**：verify-before-test gate 的指令一律貼絕對路徑（worktree 根目錄與要載入的 `dist`），並註明主 checkout 的那份是舊程式。
- **E2**：AskUserQuestion 的選項說明先寫「使用者會看到什麼」，再寫代價；推薦選項要附一句為什麼。
- **E3**：`gh` 指令直接用 memory 記的 `GH_CONFIG_DIR` 路徑，不要從設定檔動態讀。
- **E4**：上游有平行 session 在動時，第一次 review 前就先做 `wip:` commit，rebase 不用臨時處理未 commit 的工作樹。
