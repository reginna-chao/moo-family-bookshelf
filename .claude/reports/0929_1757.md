## 2 卡點與摩擦

- **U#**：無使用者糾正；每個決策都選了 TL 建議。
- **G1 — 改「誰走哪個分支」時，沒有列出同一份紀錄的所有不變式與所有寫入者，連鎖出現三個同源缺陷**：
  - 第一輪讓「空殼前管理者」的自己離開改走一般成員流程（為了不讓他解散別人的家庭）。
  - 這一改同時打破了 `family:{id}` 的兩個隱性不變式：「`members` 不為空」（`normalizeFamilyRecord` 遇空陣列會拋錯，`worker/src/kv/schema.ts:196`）與「`ownerId` 在名單上」。
  - 結果依序被找出：C1（家庭路由最後一人離開寫出空名單，orchestrator 在處理 tester 的 open question 時發現）→ C1'（`worker/src/routes/user.ts` 刪帳號寫出空名單，reviewer 重審發現）→ INFO-2（`OWNER_CANNOT_LEAVE` 意外改成依賴歸屬紀錄，可能產生沒有管理者的家庭，security 發現）。
  - 三輪 Fix Cycle 共 8 次 dispatch 都在補這一條鏈。根因：`.claude/rules/backend.md` 沒有把 family record 的不變式寫成規則，改動時也沒有「列出所有 `putFamilyRecord` 呼叫點」這一步；`user.ts` 在另一個檔案，第一輪完全沒看。
- **G2 — 讀取端拋錯的不變式沒有寫入端把關**：空名單只在下一次讀取時才爆（永久 500），寫入當下完全沒有訊號。資料存取層 `worker/src/kv/families.ts` 的 `putFamilyRecord` 是唯一 put，卻不檢查這個讀取端必然拒絕的形狀。
- **G3 — reviewer 與 security 再次互補**：INFO-2 與 INFO-4 是 security 找到、reviewer 兩輪都沒提；C1' reviewer 找到、security 列成 INFO-3（同一件事）。與 0924_1406 G2 同一個觀察。
- **執行面良好之處**：premise check 在派工前確認 #222 沒有其他 session 在處理；範圍外的 owner 權限漏洞由 coder 回報後，判定為同根因並在同一 PR 處理，沒有另開 worktree。

## 3 改進提案

- **L0929_1757-1**（對應 G1）`target=.claude/rules/backend.md | sketch=新增「family record 不變式」一節：members 永不為空（移除改走解散）、ownerId 應在名單上、member pointer 與名單雙向一致；任何改動 DELETE member／DELETE user／join 分支路由的 PR，必須列出所有 putFamilyRecord 呼叫點並逐一說明是否仍守住這三條 | status=proposed`
- **L0929_1757-2**（對應 G2）`target=.claude/rules/backend.md | sketch=資料存取層的 put 對「讀取端必然拒絕的形狀」要 fail loudly（例如 putFamilyRecord 拒絕 members: []），把永久 500 變成當下的 500，並有測試釘住 | status=proposed`
- **L0929_1757-3**（對應 G3，與 0924_1406 L2 同一條，第二次出現）`target=.claude/skills/develop/references/code-cycle.md | sketch=diff 碰到 worker/src/routes 的授權／成員資格邏輯時，security-auditor 與第一輪 reviewer 平行派出，每輪 Fix Cycle 後的重審也同時帶一次聚焦的 security 掃描 | status=proposed`
- **E1**：tester 的 open question 要當成候選缺陷在 orchestrator 端驗證（這次 C1 就是從「空家庭紀錄會怎樣」這個問題追出來的），不要直接歸為殘餘風險。
- **E2**：種入「不一致狀態」的測試 helper（`makeUser2LastListed`、`makeUser1UnlistedOwnerOfThree` 等，`worker/tests/integration/hollowMember.test.ts`）比 Proxy 交錯更便宜也更穩定，驗證授權規則時優先用它，Proxy 只留給必須證明交錯本身的案例。
