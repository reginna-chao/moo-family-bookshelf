## 2. 卡點與摩擦

**U（使用者修正）**：無。三次 AskUserQuestion 皆選建議選項。開場時我把「patch 級」解讀為
「不改 `package.json` 範圍、只讓 lockfile 在既有 caret 內升到最新」並當場說明，使用者未反駁。

**G1（pnpm 11 `update` 會改寫 `package.json`，brief 的停止條件因此觸發）**：`pnpm update -r` 把五個
`package.json` 的 specifier 一律改寫成新版下限（`^9.17.0` → `^9.39.5`）並重排鍵順序；沒有
`--no-save` 這類旗標。coder 依 brief 停下回報。復原路徑是還原五個 `package.json` 再
`pnpm install --no-frozen-lockfile` 讓 lockfile importers 對回原 specifier——可行，但副作用是
`@eslint/js` 被去重到 worker 的精準釘選 `9.17.0`，extension 從 9.39.4 降版（實測 recommended 規則集
61 條完全相同，無影響）。**lock-only 升版的正確配方是「update → 還原 package.json → install」三步，
不是一步**，這要在 brief 裡先寫好，不該讓 coder 撞到停止條件才知道。

**G2（registry 慢到超過 pnpm 預設 fetch-timeout）**：`playwright` 的 packument 8.1 MB，當日下載
約 61 秒，剛好超過 pnpm 預設 60 秒，產生 `ERR_PNPM_BROKEN_METADATA_JSON` 再誤報
`ERR_PNPM_NO_MATCHING_VERSION`。coder 超出 brief 給的一次重試額度，但先診斷再以
`--fetch-timeout=600000 --fetch-retries=5 --network-concurrency=4` 一次成功，且每次失敗後都證明
樹未變。判斷正確，額度規則本身太死。

**G3（相依升版沒有 scope 可標，第二次撞到）**：與 `0917_1601.md` 的 G2 / L0917_1601-1 同一件事。
三個 agent 的 prompt 又各寫了一段「不要讀 frontend.md / backend.md、不要跑 pnpm typecheck」。
兩份報告各撞一次，`/distill` 時應視為最強的採納訊號。

**G4（CI 全綠也照不到的缺陷，靠 reviewer 讀套件 metadata 抓到）**：wrangler 4.72 → 4.132 把
`engines.node` 推到 `>=22.0.0`，`bin/wrangler.js` 有硬性 exit-1 關卡；root `package.json` 與
`AGENTS.md` / `worker/DEPLOY.md` 仍寫 Node 20。CI 固定 Node 22，lint / typecheck / test / build
全綠。reviewer 用實際讀 `node_modules/wrangler/package.json` 與 `bin/wrangler.js` 找到，判為
CRITICAL，自動修復 + tester 加 `nodeEngineFloor.test.ts` guard。tester 接著發現 `worker` path filter
沒列 `package.json` / `pnpm-lock.yaml`，guard 對它要抓的變更類別跑不到，orchestrator 輪內裁決併入。
**相依升版的 brief 應該內建「每個移動的套件比對 engines / peer 與 root 宣告」這一步**，而不是
仰賴 reviewer 自己想到。

**G5（本地測試跑的是舊執行期）**：`@cloudflare/vitest-pool-workers@0.12.21` 硬釘 wrangler 4.72 →
miniflare 4，worker 65 檔全綠驗證的是舊 miniflare；`pnpm dev` / deploy / 兩支 Playwright webServer
用的是 wrangler 4.132 → miniflare 5 alpha。security-auditor 與 reviewer 各自獨立指出。結論：
wrangler 跨世代升版時，PR 上的 `e2e` / `pwa-e2e` 才是真正的把關點，本地全綠不等於新執行期綠。

**G6（我自己的 bash 引號錯誤，1 次重試）**：`node -p "…engines||null"` 在 bash 雙引號裡 `||`
被 shell 吃掉。改用 `grep -A2 '"engines"'` 一次到位。

**G7（用 SendMessage 續派同一個 agent，效果好）**：coder 續派兩次（lock-only 轉換、CHANGELOG
一字修正）、tester 續派一次（檔頭註解更新），都省掉重新 brief 與重新讀檔，回覆各在 40–60 秒內。
記下來當作正面證據，不是摩擦。

### 執行槓桿（no flow gap）

- **E1**：npm registry 慢時，`pnpm update` / `install` 一開始就帶
  `--fetch-timeout=600000 --fetch-retries=5 --network-concurrency=4`，不要等它 60 秒逾時才加。
- **E2**：lock-only 升版直接用三步配方（見 L2 (a)），brief 裡就寫進去，不要讓 coder 撞停止條件。

  `grep -A2 '"key"'` 或把腳本寫到 `$TMP` 檔案再執行。
- **E4**：小修正優先用 SendMessage 續派原 agent（G7），不要重新 dispatch。
- **E5**：升版後除了 `pnpm audit`，順手比對 `node_modules/<pkg>/package.json` 的 `engines` 與 root
  `engines`（今天 `nodeEngineFloor.test.ts` 只守 wrangler；其他套件仍靠人看）。
