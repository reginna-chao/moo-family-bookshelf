## 2. 卡點與摩擦

**U#（使用者更正）**：本次 run 中途無使用者更正——非互動模式，使用者僅在收尾 gate 做三項決策（提交並開 PR／做 retro／既有問題下一任務再修）。

**G1 — 跳過 verify-before-test gate，導致整輪測試白寫。**
R1 的 coder 產出後直接派 tester；R1 的 reviewer 隨後判 CRITICAL、整個設計被換掉，tester R1（344s）的產出（3 改寫 + 3 新增）在 R2 全部作廢重寫（707s）。code-cycle.md 的 gate 設計是「使用者手動驗證」，而這是純後端安全變更、沒有可點擊的 UI 表面，我因此略過——但該 gate 真正要防的「對未確認的行為寫測試」風險完全成立。約 1050s 的 tester 工時可由一次 reviewer design-check 換掉。

**G2 — 直接採用 auditor 的建議修法，未先驗證其信任模型。**
原始 finding 的建議是「只有當 userId 是目標 family 的現有成員時才累加 failCount」。實作後 reviewer 立刻證明無效：`isExistingMember` 不是「請求者是本人」的訊號，攻擊者改打**受害者自己的 familyId** 即可，而 familyId 可由公開未驗證的 `POST /api/auth/lookup`（`worker/src/routes/auth.ts:74`）用 userId 直接查到。原 finding 宣稱的前提「受害者不在任何家庭」其實把受害範圍寫反了——真正中招的是**所有已加入家庭的使用者**。一次 grep 公開端點就能在動工前推翻該修法。

**G3 — SUGGESTION 決策 gate 與非互動 session 衝突。**
skill §2 要求 SUGGESTION 一律用 AskUserQuestion 讓使用者決定；本 session 明示使用者不在線上、提問會卡住工作。我自行採用 🟢 項、延後純重構項，再把所有決策併入收尾 gate。流程檔目前沒有描述這個分支，下次仍會踩同一個判斷。
