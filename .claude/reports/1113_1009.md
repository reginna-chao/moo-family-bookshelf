# Retro 1113_1009：存著的 token 記下發給它的伺服器

分支 `fix/stored-token-issuer`。這是一個安全修正，報告不寫觸發方式，細節記在私密的 Security Advisory。修法是新增本機欄位 `moo:authTokenServer`，寫 token 時同時記下發行的伺服器；讀 token 時，記錄和目前的端點對不上就不使用。

## 2. 卡點與摩擦

- **G1：原本的修法方向會帶出另一個問題。** 公告建議「把 token 和端點放在同一次寫入」。分析時發現，這樣做的話，晚到的寫入會在家庭拆除之後把舊端點寫回去，留下沒有家庭的孤立端點，正是 #498／#501 處理的那類問題。最後改採「記錄發證伺服器」。這一步是 `code-cycle.md` Phase 1 step 2「文件只是線索」擋下來的，規則已經存在，所以不另外提案。
- **G2：沒有標記就照常使用，等於失敗時放行，而計畫的第一版驗收沒有測到這一點。** 金魚 Round 1 的 R1 指出：只要任何一個讀取點的 `get` 漏讀標記鍵，修正在那一處就會無聲失效，而第一版驗收全部仍然會是綠的。補上的做法有兩個：所有讀取點共用 `STORED_SESSION_KEYS`，並且每個讀取點都要經過真正的讀取路徑來驗收。tester 的突變證據顯示，`readKeys` 突變確實會讓那些測試變紅。
- **G3：文件要改的地方，花了兩輪金魚審查才列齊。** Round 1 的 D1 補了 5 句，Round 2 又補了 R10 的 4 處和 D7 的 1 處。原因是計畫只列出我記得的段落，沒有用 grep 找出所有描述這個機制的句子。
- **G4：GO 之後 main 前進兩次。** 派 coder 前是 #504（它新增的撤回邏輯多了一處 token 清除），派 tester 前是 #506（沒有重疊）。兩次都在派工前的 base re-check 抓到，分支都還沒有 commit，所以直接快轉。#504 那次另外在 PLAN.md 加了一節「GO 後的基準更新」，處理行號對照和第三處清除，沒有重跑金魚。
- **G5：session 在 SUGGESTION 決策時被中斷，兩天後重啟。** 靠 PLAN.md 的 `接續點` 和 Fix Cycle Log 直接接上，沒有重做任何一個階段。中斷前還在跑的測試檔審查，報告也有送達。
- **G6：tester 跑了 27 分鐘。** 6 項驗收各要做突變證據，涵蓋 14 個既有測試檔。結論正確，但時間是這次 run 最大的單一成本。
