## 2. 卡點與摩擦

- **G1：Issue 的清單漏了一組重複檔。** #208 列了 3 組，Phase 1 重新列舉後找到第 4 組：`extension/src/dialog/familyShelfPrefs.ts` ↔ `pwa/src/hooks/familyShelfPrefs.ts`，兩份只差 import 路徑。「Verify cited specifics」這一步照設計發揮作用，不需要提案。
- **G2：coder 用了 `git rm` 刪檔。** 這個指令不在 permission allow list 裡，刪除因此直接被 staged。coder 在回報中自己揭露了這件事。刪檔本來就在需求裡，orchestrator 直接採用；但 coder 的角色定義沒有說刪檔要用什麼方式。
- **G3：新 worktree 沒有 `node_modules`。** 量測試基準之前得先跑 `pnpm install`，Phase 0 沒有提到這一步。
- **G4：run 進行中 `origin/main` 前進了一個 commit（#218），而且改到同樣的 `AGENTS.md` 和 `docs/project-plan.md`。** 當時所有變更都 staged、還沒 commit，沒辦法直接 rebase。處理方式：先把 patch 備份到 scratchpad，用帶 tag 的 stash 暫存，`merge --ff-only` 之後 `stash apply --index <sha>`，最後依 sha 找回並 drop 那個 stash。自動合併沒有衝突。code-cycle 只寫了「rebase/ff」，沒有涵蓋「全部 staged、尚未 commit」的情況。
- **G5：orchestrator 在 coder prompt 裡把一個 bug 寫成了「必須保留的行為」。** 原文是「An error-envelope response (no data) still counts as loaded」。tester 之後發現，正是這個行為會讓伺服器上的偏好被整批覆蓋（#219）。純重構保留它是對的，但 prompt 當時應該同時把它標成可疑點，讓 reviewer 或 tester 當場分級，而不是等 tester 自己碰巧發現。
- **G6：沒有量重構前的覆蓋率。** 把被測到的程式碼從 `src/**` 搬出 coverage 的 `include` 會改變分母，tester 只能報告搬完之後的數字（都遠高於門檻，這次沒有影響）。
