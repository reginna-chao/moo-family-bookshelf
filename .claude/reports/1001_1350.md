## 2. 卡點與摩擦

- **U1**：使用者在 verify-before-test 關卡問「這是在哪個 worktree 專案?」。關卡說明只給了 repo 內相對路徑 `.claude/worktrees/resolve-issue-245-e8b03f`，沒有一開頭講清楚「哪個專案、哪個 worktree 名稱、要在那裡開終端機和載入 `extension/dist`」。
- **G1**：fix mode 預測失準。預估 ≤ 40 行，實測 63 行。原因是把兩個選項的 inline `onClick` 抽成 `handleSelect`、改寫兩份 JSDoc，這類「改寫」同時算新增和刪除，行數是兩倍。升級後多了一個手動驗證關卡和完整 review／安全掃描。
- **G2**：issue 前提與程式不符。issue 說 Extension 的排序和「⋯」選單 Esc 後焦點掉到 `<body>`，但兩者早就各自還原焦點且有測試（`extension/src/dialog/BookSortDropdown.tsx:82`、`extension/src/dialog/OverflowMenu.tsx:85`）。Phase 1「驗證外部提供的清單」這條規則有接住，沒有造成返工。
- **G3**：預設值翻轉帶來退步（S1）。`returnFocusOnEscape` 改成預設 true 後，inline 選單開著時使用者 Tab 到搜尋框再按 Esc，焦點會被搶回按鈕。需求分析時只看「誰要這個行為」，沒看「Esc 當下焦點可能在哪」，由 reviewer 用 jsdom 重現後才抓到。
- **G4**：`origin/main` 在 run 中前進（#247）。安全掃描依 Phase 6 用 `base_ref: origin/main`，`git diff --cached origin/main` 把 #247 反向列出，auditor 得自己察覺並改用 HEAD 比對。Phase 4 開頭的「派 review 前 fetch 一次」也沒做。
- **G5**：tester 的 mutation check 會暫時改動工作樹的正式程式碼，與平行的 reviewer 撞在一起，reviewer 第一輪看到 `MM` 狀態。因為 prompt 已要求只看 staged，沒有造成誤判；第二輪改成明確要求 `git show :<path>`。
