## 2. 卡點與摩擦

- **G1 reviewer 可以更早派**：coder 回來、暫存之後 production code 就凍結了，code-cycle Phase 3 step 4 允許 tester 與 reviewer 平行；這次 reviewer 等 tester 跑完才派，多串了 284 秒。fix mode 的流程條列（coder → verify → tester → reviewer）讀起來像是必須串行，實際上沒有這個限制。
- **G2 tester 的 red-before 探針放在 `extension/src/` 下**：tester 用 `git show HEAD:…` 把修正前的 hook 存成 `src/dialog/zzPreFix281UseAutoSetup.ts` 來證明測試修正前會紅。orchestrator 在 tester 跑到一半時量測 fix-mode 條件，`git status` 看到 `extension/src/` 下有 untracked 檔，依規則這會把 run 升級成 full cycle；因為知道是探針才沒升級。探針最後有刪乾淨，但規則與做法有衝突。
- **G3 coder 第一次回報才發現兩處過時 JSDoc**：`useAccountGate.ts` 與 `AccountCheckContext.ts` 的註解描述的是舊行為，coder 正確地只回報不動（不在指派的 files 內），多一次續派（88 秒）。派工時只列了會改程式的檔案，沒有把「描述這個行為的註解」一起算進去。
- **G4 SUGGESTION 分級不一致**：reviewer 把「測試沒釘住抓書單與確認的順序」判 P0，理由是未來重構可能把順序改掉。change-triage 的門檻是「今天能不能寫出會失敗的檢查」——今天順序正確，寫不出來，所以是 P2。orchestrator 照 change-triage 判，沒有列。
- **U# 使用者修正**：無。使用者只在開頭送了一句「解決」。
