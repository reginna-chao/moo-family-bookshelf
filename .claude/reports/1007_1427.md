## 2. 卡點與摩擦

- **G1 平行 coder 的文件所有權**：兩個 coder 都要把理由搬進 `docs/architecture.md`／`frontend.md`，但同一檔案不能有兩個 owner。採用的做法：A 直接擁有文件；B 把每段理由寫進 scratchpad 的暫存檔（每段標 `TARGET: <檔案> → <既有標題> (append)` 或 `NEW "<標題>" placed after "<錨點>"`），B 的程式註解直接指向它自己命名的標題；之後整合 coder C 逐段原文貼入、再對 staged diff 裡所有指標做解析檢查（67 行逐字比對 missing=0、指標全部解析）。有效，但多了一個 dispatch 與 7 分鐘。
- **G2 上限表的單一 owner**：`extension/eslint.config.js` 的 `MAX_LINES_LEGACY_CEILINGS` 有 23 筆，A／B 都會縮短表裡的檔案，所以兩者都被禁止碰它、ratchet 測試在整合前預期為紅；C 以 `wc -l` 重量全部 23 筆統一更新。沒有出錯，但這條規則要在 A／B 的 prompt 裡明講，不然任一方跑 `pnpm test` 會看到紅燈去「修」。
- **G3 連續四批、唯一的發現類型相同**：reviewer 抓到的 S1／S2 又是「寫進 docs 的句子與程式碼不符」（第 1 批 CRITICAL、第 2～4 批 SUGGESTION）。第 2 批 retro 的 L1007_1053-1 已提案把這點寫進 code-cycle 的 reviewer prompt；本批 reviewer prompt 已照做，所以抓得到——問題在 coder 端仍會寫出來。
- **G4 coder 順手更正過時註解**：A／B 共發現 8 處舊註解已與程式碼不符（familyId 讀取順序、手機版按鈕位置、斷點 767px、斷路器呼叫端、`ensureOnLibraryPage` 會導航、`refreshToken` 回傳型別、displayName 寫 sync 但沒人讀、`familyEndpointChoice` 的呼叫端）。這些「更正」是 coder 的主張，必須由 reviewer 逐一對照程式碼——本批 8 處全部屬實，但 prompt 要明講「更正要列出來給 reviewer 查」。
- **G5 第 1 批 PR 的量測表與 issue 表對不上**：issue #255 的表用舊算法（空一行接 `export` 的 JSDoc 也算），本批起 PR 內文都標明「修正後算法」並重述盲點。

## 3. 改進提案

**Flow-structural**

- L1007_1427-1：`target=.claude/skills/develop/SKILL.md §3（平行派工那段）| sketch=補一條「平行 coder 需要共同寫入同一份文件時」的做法：一方直接擁有文件，另一方把要加的段落寫進 scratchpad 暫存檔（每段標 TARGET 既有標題或 NEW 標題＋錨點），程式內的指標直接用那些標題；之後由整合 coder 原文貼入並對 staged diff 的所有指標做解析檢查。同理，任何「兩邊都會改到的單一表」（eslint 上限表）在平行期間禁止兩方碰，由整合步驟統一更新 | status=proposed`
- L1007_1427-2：`target=.claude/agents/coder.md | sketch=「改寫註解時發現舊註解與程式碼不符」的處理：不要把錯誤搬進文件，照程式碼實際行為寫，並在回傳的獨立小節列出每一處更正（原句／程式證據 file:line／新句），讓 reviewer 能逐一核對 | status=proposed`
- 不提升：G3。L1007_1053-1 已涵蓋 reviewer 側；coder 側的「寫進 docs 前重讀程式碼」本批 prompt 已明講，仍出現 2 處，屬於需要 reviewer 把關的殘餘，不再加規則。

- E1：拆平行 coder 時用「目錄 × 區塊數」切，讓兩邊牆鐘接近（本批 A 175 區塊／B 150 區塊，兩者都約 22 分鐘），整合步驟才不會等太久。
