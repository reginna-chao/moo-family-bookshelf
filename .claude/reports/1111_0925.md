## 2. 卡點與摩擦

- **G1：這個 run 本身就是摩擦。** 上一個 run 的 Fix Cycle Round 1 為了行數上限，把另一份已記錄修正所依賴的那段比對換成新機制，新機制多做了一件舊機制刻意不做的事。當時向使用者說明了行為差異，但沒有把差異對回那份修正的「不修的後果」；reviewer 兩次、security-auditor 兩次都沒有指出。直到合併後使用者問要不要更新 advisory、我重讀另一份 advisory 的修法時才發現。
- **G2：被改寫的測試斷言就是警訊，卻沒被當成警訊。** 上一個 run 的 tester 依指示把既有案例裡「新伺服器沒有收到任何請求」改成「收到一次讀取」。一條安全性質的否定斷言被放寬，這件事本身應該觸發「這條斷言是哪一份修正的回歸測試」的檢查。
- **G3：focused review 等了約 47 分鐘。** 審查對象是 23 行的測試改動；agent 起了自己的背景工作並停在等待，中途回來的是「尚未報告」的通知。最後結論是 PASS、無發現。
- **G4：main 在驗證後前進一次**（#504），無重疊，快轉後整套重跑。流程照規則走，成本是多一次全套測試。

使用者沒有糾正或打斷（U# 無）。

## 3. 改進提案

**Flow-structural**

- `L1111_0925-1`：target=`.claude/skills/develop/references/code-cycle.md`（Phase 4 → Fix-round handoffs → Behavior handoff）| sketch=fix 會放寬或刪掉既有測試裡的否定斷言（「沒有送出」「沒有收到」）時，先用 `git log -S` 找出那條斷言是哪個 commit／PR 加的、它保護的是什麼，把結論寫進 Fix Cycle Log 並告知使用者；找不到出處才視為一般改動 | status=proposed
- `L1111_0925-2`：target=`.claude/skills/develop/references/code-cycle.md`（Phase 4，Fix-Cycle 偏離已 GO 計畫時）| sketch=fix 輪偏離計畫裡明寫「原樣保留」的項目時，這是使用者決策，不是事後揭露：先問再派 coder | status=proposed
- `L1111_0925-3`：target=`.claude/agents/reviewer.md`（focused 審查）| sketch=focused 審查不起背景工作；需要長時間 probe 時先回報並說明，由 orchestrator 決定 | status=proposed
- 安全修正之間互相依賴的清單：不提升。這類資訊是未公開的，不能寫進 git 追蹤的檔案；L1 用斷言的出處來抓同一件事，不需要清單。

**執行槓桿**

- `E1`：把「行為差異」告訴使用者時，同一句話要說出它讓誰多收到了什麼（對象＋資料），不只說「不帶秘密」。
- `E2`：合併後更新 advisory 之前，先重讀同一個檔案相關的其他 advisory 的「修法」段，確認這次的改動沒有讓它們失真。這次是這一步抓到 G1 的。
- `E3`：dispatch 超過前幾次同類派工時間的 3 倍、且回來的是「等背景工作」時，主動告訴使用者並給選項，不默默等。

## 4. Skill／Agent 增減建議

- 不增不減。fix mode 對這種 30 行、規格逐字給定的修正是合適的：4 次派工，沒有重工。
- reviewer 對正式檔的審查（12 個 probe 情境，約 13.5 分鐘）有價值；對 23 行測試改動的 focused review 沒有產出發現，卻是整個 run 最慢的一步。規則要求它，提案 L3 處理的是時間，不是存廢。
