## 2. 卡點與摩擦

- **G1**：五個 agent（tester×2、reviewer×2、auditor）同時被 session 用量上限（HTTP 429）打斷。鑑識結果：frontend tester 的磁碟成果完整（兩個測試檔、98 案例全綠、涵蓋規格每一項）直接採用；backend tester 什麼都沒留下；三個唯讀 agent 直接重派。證據：五則 `rate_limit` task-notification；`git status` 只有 `extension/tests/unit/` 兩個檔案有改動。
- **G2**：第一輪安全掃描 PASS，但 backend reviewer 隨後抓到 CRITICAL：墓碑清單只限筆數（1000）不限每筆長度，`isRealBookId` 的 `\d{12,}` 沒有上限，使用者可用 190 萬位數的 id 交替 PUT 把自己的紀錄撐到 KV 25MiB 上限。auditor 自述漏掉的原因：把 `isRealBookId` 下意識當成長度上限，沒算「筆數 × 單筆最大長度」，也沒查單次 body 上限管不到跨請求累積的狀態。證據：reviewer 用 `createMockKV()` 實跑 12 次 PUT → 11.4MB。
- **G3**：frontend coder 被交辦在 `shared/src/api/types.ts` 加一個選填欄位，但該檔正好在 `MAX_LINES_LEGACY_CEILINGS` 的 206 行上限，coder 自行還原並回報。orchestrator 派工前沒查 headroom（code-cycle §3 已要求「state the file's headroom」，這次沒做）。結果：不加欄位，程式碼本來就走 `Record<string, unknown>`。
- **G4**：兩個 tester 都在檢查 EOL 時對新檔做了 `git add -N`，違反 agent 不碰 git 的規則；無害（正常 staging 覆蓋），但兩次都發生。證據：兩份 tester 回報的「Process slip」。
- **G5**：auditor 聚焦重掃時被要求「找同類問題」，找到範圍外的既有 WARNING（`familyShelfPrefs` ref 長度無上限，#316）。這是第一輪 `full` 掃描也沒看到的，只有在被明確要求找「筆數有上限、byte 沒上限」這個類型時才找到。

## 3. 改進提案

### Flow-structural

- **L1013_1629-1** `target=.claude/agents/security-auditor.md | sketch=Dimension 6 加一條固定檢查：任何跨請求保留的伺服器狀態（清單、集合、計數）要同時算「筆數上限 × 單筆最大 byte」，單次 body 上限不算數；regex 的 {n,} 不是長度上限 | status=proposed`（對應 G2、G5；reviewer 這次靠實跑才抓到，應變成 auditor 的固定項目）
- **L1013_1629-2** `target=.claude/agents/tester.md | sketch=驗證 EOL 的指定做法改成不需要 index 的指令（例如 file 或 od -c，或只對已追蹤檔用 git ls-files --eol），並明說 git add -N 也是 git 寫入 | status=proposed`（對應 G4；兩個 tester 同一天同一個滑脫）
- **L1013_1629-3** `target=.claude/skills/develop/SKILL.md | sketch=§3 dead-agent 段補一句：多個 agent 同時因 429 死亡時，先對有寫入權的 agent 做鑑識並採用完整成果，唯讀 agent 等限額重設後一次重派；這次照現有規則做對了，但規則沒寫「同時多個死亡」的順序 | status=proposed`（對應 G1）
- 不提升 G3：code-cycle §3 已有 headroom 規則，是 orchestrator 這次沒執行，不是流程缺口。

### 執行槓桿

- **E1**：派 coder 改任何 `shared/src/` 或 pinned 檔案前，先 `wc -l` 對照 `MAX_LINES_LEGACY_CEILINGS`，差距寫進提示；這次少做一次 `wc -l` 換來一個 coder 回合。
- **E2**：reviewer 提示裡「風險清單」的大小項目要寫成可計算的式子（「1000 × 每筆最大長度 = ?」），不要寫結論（「約 18KB」）；這次 orchestrator 自己先算了 18KB，把錯誤的前提傳給了 coder 和 auditor。
- **E3**：全套測試由 orchestrator 依序跑一次（worker → extension）、tester 只跑自己的檔案，這次運作良好，沒有 CPU 爭用假紅；維持。
- **E4**：session 用量上限重設前，orchestrator 可先做不需要 agent 的工作（鑑識、E2E typecheck、base re-check）；這次有做，省下一輪等待。

## 4. Skill / Agent 增減建議

- **security-auditor**：Dimension 6 補「累積型狀態的 byte 上限」固定檢查（L-1）。這次第一輪 PASS、reviewer 抓到 CRITICAL，是 auditor 應該先抓到的類型。
- **tester**：EOL 檢查改法（L-2）；另外兩個 tester 的變異測試（複製 service 刪一條規則、確認恰好對應的案例變紅）品質很高，可寫進 tester.md 當建議做法。
- **reviewer**：維持。backend reviewer 用 mock KV 實跑 12 次 PUT 重現 C1，是這次最有價值的發現。
- 不新增 agent。
