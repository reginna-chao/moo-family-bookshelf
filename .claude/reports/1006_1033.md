## 2. 卡點與摩擦

- **G1 fix mode 預測失準，原因是檔案剛好卡在 max-lines 上限**：`extension/src/content/index.ts` 是 456 行，等於 `extension/eslint.config.js:17` 的 ceiling。邏輯上只改一行呼叫，但 import 多一個名稱被 prettier 換成多行（+4），為了抵銷又縮了一段註解（−4），12 行純粹是為了守上限的搬動；加上新函式的 JSDoc 與 docs 兩條，總數 53 行。預測時沒有把「被改的檔案在 ceiling 上」算進行數。升級本身依規則順利進行，沒有重跑任何階段。
- **G2 reviewer 的 S1 分級落在規則的縫隙**：reviewer 老實寫「不是 P0/P1」，但 S1 是這次 diff 自己引入的行為退步（舊的重新注入會清掉離開家庭後的數字，新路徑會留著）。`change-triage.md` 的 P0/P1 關卡是針對「使用者沒要求的改善提案」，對「這次改動自己造成的退步」沒有明說；orchestrator 以「這是修正本身的正確性」判定納入，但這是解讀，不是規則。
- **G3 tester 的 `git add` 被 auto mode 的權限分類器擋下**：tester 依指示要 `git add` 新測試檔，被拒後正確地沒有繞過，改在回報裡要求 orchestrator 暫存。orchestrator 先看過 diff 再暫存，沒有問題，但同一件事在 coder 那邊卻通過了（coder 的 `git add` 成功）。agent 的 `git add` 結果不可預期，每次都得在回報裡確認。
- **G4 第一次安全掃描與 reviewer 平行，S1 修正後需要重掃**：規則本來就允許小 diff 平行並在 Fix Cycle 後重掃變更檔，重掃只花 23 秒，成本可接受；記下來是因為這次「平行」省下的時間（約 100 秒）與重掃成本相當，對小 diff 不一定划算。
- **U1 無**：使用者整輪不在線，commit gate 一次回答三題（commit／S1 追認／retro）。
