## 2. 卡點與摩擦

- **U1（使用者修正範圍）**：「Worker 也有問題嗎?」「有問題的都一起處理」。我在範圍問題裡把「只修 PWA」列為建議選項，把 Worker 當成替代方案；使用者先選了「PWA + Extension 一起修」，接著主動追問 Worker。Issue 內文其實已經點出 `worker/src/routes/family.ts` 的兩個位置，根因在伺服器，我卻把建議選項放在用戶端。
- **G1（規格重做，本次最大的浪費）**：Phase 1 我設計了「自己離開時寫 10 分鐘標記」的規格並取得確認。後端初審指出每個帳號只有一組 token，另一台裝置在 10 分鐘後一樣會被加回。改成「帶 `recovery: 1` 且不在名單上就拒絕」之後，不需要任何 KV 資料。作廢的工作：後端 coder 第一輪的標記實作、後端 tester 第一輪的 70 個測試、後端初審的大部分內容，共 3 次 dispatch。更簡單的規則在 Phase 1 就想得到，只要先問「不在名單上的人送背景重新加入，有沒有任何正當情況」。
- **G2（單一 token 的事實太晚進入設計）**：`worker/src/middleware/auth.ts:78-91` 的「發新 token 會撤銷舊的」直到 verify 關卡才被我查到（前端 coder 的 open question 帶出來），結果多一輪 coder 補「離開請求自己收到 401 時放行重試一次」。G1 和 G2 是同一個根因：Phase 1 的 surface matrix 沒有列「同一帳號的其他裝置／其他 session」。
- **G3（tester 在舊規格上跑完）**：後端初審回報 S1 時，後端 tester 還在寫標記的測試。我選擇讓它跑完再問使用者，70 個測試全部作廢。當時我已經建議改規格，應該先停掉它。
- **G4（本機實測的環境坑）**：`wrangler dev` 不帶 `--var DEV_MODE:1` 時，速率限制的模擬 binding 每個請求都回 500；改用 `extension/playwright.config.ts:40` 的啟動方式才正常。另外家庭上限是 2 人，實測腳本第一版因此在第 9 步之後全部 `FAMILY_FULL`。兩件事各多一次重跑。
- **G5（實測沒有跟著規格更新）**：16 項 API 實測是針對 10 分鐘標記做的。改規格後我沒有重跑（腳本還在 scratchpad，改兩行就能用），只靠整合測試。已在完成報告揭露。
- **G6（錯誤碼命名）**：我先向使用者提了 `NOT_A_MEMBER`，派工前 grep 才發現 Worker 已有 `NOT_FAMILY_MEMBER`，改用 `RECOVERY_NOT_MEMBER`。對使用者說出口的名稱和最後的名稱不同。
- **G7（文案來回）**：`REVERIFY_LOGOUT_MESSAGE` 的起始文案是我在 coder prompt 裡給的，只對 #263 的情境成立，對最常見的觸發情境（開啟 PWA 時的背景載入）不成立。S1 複審抓到後多了 coder、tester 各一次 dispatch。
- **G8（行數上限的連鎖成本）**：`pwa/src/api/client.ts` 縮短 2 行，上限要跟著降，而 `eslint.config.js` 不在第一輪 coder 的檔案清單裡，多一次專門的 dispatch。之後的 prompt 我把兩個 `eslint.config.js` 列進負責範圍，就沒有再發生。
- **G9（文件由 orchestrator 直接改）**：D1／D2 是純文件修正，我直接用 Edit 改 `docs/architecture.md` 和 `.claude/rules/backend.md`，再跑 prettier 重排表格。省了一次 dispatch，但 skill 沒有明說 orchestrator 能不能改文件，這次是我自己判斷屬於「pure doc change」例外。

### 執行槓桿（no flow gap）

- **E1**：向使用者提出新的錯誤碼、欄位名或 KV key 之前，先 grep 三個套件有沒有相近的名稱。
- **E2**：在 coder prompt 裡給文案起始稿時，先用「最常觸發這段文字的情境」檢查一次是不是事實，不要只對照 issue 的情境。
- **E3**：規格改變後，把 scratchpad 裡的實測腳本改成新規格再跑一次，成本是一個指令。
- **E4**：範圍問題的建議選項，要對照 issue 自己列的位置；issue 已經指出伺服器端的根因時，建議選項不該只修用戶端。
- **E5**：reviewer prompt 裡明確要求「逐一列舉合法使用者會不會被新規則鎖在外面」，這次後端複審因此產出了完整的狀態分析，值得當成新增存取規則時的固定問題。

- **新增候選**：無。這次的浪費來自規格設計，不是缺少角色。
