## 2. 卡點與摩擦

- **U1 使用者介入：「請問已經測試將近兩個小時了，是真的有在測試嗎? 還是我可以重新開機?」** tester #1 在跑完整測試時，32 個與本次改動無關的測試檔全部以 `(0 test)` + `Test timed out in 30000ms` 失敗，單一測試檔要 166–175 秒（正常不到 1 秒）。tester 停下前的最後狀態是「正在確認這些是不是載入逾時」——它在追查環境問題，而不是回報。orchestrator 沒有任何機制察覺一個 dispatch 跑得異常久，直到使用者發問才用 scratchpad 檔案的時間戳判斷它還活著。中止後以 `git status`／`git diff` 回收它寫好的 3 個測試檔（SKILL.md §3 的 forensics 路徑），正式程式碼未受影響；紅燈證明由 orchestrator 補做。
- **U2 使用者中途換模型並要求第二視角：「我剛剛前面都用 Opus 處理，請你最後用 Fable 角度審查是否有要調整」。** Fable 視角重看 production diff、測試、四個呼叫點與收尾路徑，結論與 reviewer 一致：程式碼不改，只有兩處文案。多做的事是自己重做兩次紅燈證明（tester #1 被中止前沒回報）。對使用者的價值：在不重派 reviewer 的情況下多一層獨立確認。
- **G1 fix mode 預測失準**：預測 ≤ 40 行，實測 50 行。多出來的幾乎全是 `accountIdentityCheck.ts` 的檔頭 JSDoc 與 `cachedIdentity` 的 JSDoc（+28 行中約 18 行是註解）。這個檔案的檔頭就是 #277／#281 行為的說明文件，改行為就必須改檔頭。升級本身依規則就地完成，沒有重跑任何階段。
- **G2 run 開始前先停一次**：issue #284 是 #281 的後續，指的程式碼（`cachedIdentity`、`handleFamilyJoined` 用它）只在當時還沒合併的 PR #285 上。Phase 0 的 premise check 抓到了，orchestrator 問使用者要疊在 #285 上還是等它合併；使用者選等。這是正確的停法，但代表「issue 寫明是某 PR 的後續」時，應在讀 issue 的同時就查該 PR 狀態，而不是讀完程式碼才發現。
- **G3 orchestrator 自己做紅燈證明時 sed 誤中兩行**：`App.tsx` 的開機路徑與 `handleFamilyJoined` 用了一字不差的 `setView(identity === "mismatch" ? "account-mismatch" : "main")`，sed 把兩行都改回去，多紅了 3 個 #271 的舊測試。新測試該紅的那一個有紅，證明仍成立，但判讀時要先排除副作用。
- **G4 security-auditor 的 `mode: changed` 假設有 commit**：變更只在 staged 區，`git diff --name-only origin/main...HEAD` 是空的，auditor 自行改用 `git diff --cached`。這次它處理對了，但這是靠它的判斷，不是 prompt 寫明。

## 3. 改進提案

**Flow-structural**

- L1006_1719-1：`target=.claude/agents/tester.md（step 6 全套測試那段）| sketch=加一句：一次 run 裡多個與本次改動無關的測試檔以「(0 test)」+ 逾時失敗，是機器負載訊號而非測試缺陷——立刻在回傳裡回報這個特徵（檔數、逾時秒數、單檔耗時），不重跑、不追查，交回給 invoker 決定重開機或等待 | status=proposed`
- L1006_1719-2：`target=.claude/skills/develop/references/code-cycle.md（Phase 0 step 5 premise check）| sketch=issue 內文寫明「#NNN 的後續」或引用的 file:line 在 origin/main 上不存在時，先查該 PR 狀態（open → 問基底；merged → 照常），把這個判斷放在讀程式碼之前 | status=proposed`
- 不提升：G1（fix mode 預測失準）。量測是權威、升級就地完成、沒有重工，規則運作如設計；要 orchestrator 預先估 JSDoc 行數反而增加預測成本。
- 不提升：G3（sed 誤中兩行）。屬 orchestrator 執行手法，見 E2。
- 不提升：G4（auditor 的 diff 基底）。auditor 已自行處理；派工 prompt 寫一句「變更在 staged 區」就夠，見 E3。

**執行槓桿**

- E1：dispatch 一個預期要跑完整測試的 tester 後，若超過該套測試正常時間的 3 倍（extension 約 5 分鐘）仍無回報，`ls -la --time-style` 看它 scratchpad 的輸出檔時間戳與大小，而不是等使用者問；整批 `(0 test)` 就直接中止、回收、重開機後自己補跑。這次的 memory 已記下這個特徵。
- E2：orchestrator 自己做紅燈還原時，用 Edit 工具配唯一的上下文錨點，或先 `grep -c` 確認目標字串在檔案裡只出現一次，再用 sed。
- E3：security-auditor 的 prompt 在變更尚未 commit 時寫明「變更在 staged 區，用 `git diff --cached`」，省掉它自行判斷的一輪。
- E4：使用者要求「換個模型／角度複審」時，orchestrator 的複審動作要可驗證：重做紅燈證明、逐條核對 reviewer 的事實主張（這次核對了 `AccountMismatchScreen.tsx:45` 的那句話確實存在、沒有測試釘住），而不是只重讀 diff 給意見。
