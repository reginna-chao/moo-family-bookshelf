## 2 卡點與摩擦

- **U#**：無使用者糾正。範圍抉擇時使用者選了選項外的「params，body 另開 issue」，屬正常決策。
- **G1 — issue 裡的「影響評估」前提不成立**：#227 是我在 #212 那次 run 寫的，issue 寫「改由 zod 驗證後，400／401 的先後順序會統一成格式先於 401，屬於 API contract 變動」。Phase 1 查 `worker/src/middleware/auth.ts:28-49` 才發現：受保護路由的 401 早就由全域 `authMiddleware` 在任何 route validator 之前回應，handler 內的 401 只是防禦碼，所以實際上沒有 contract 變動。寫 issue 時只看了 handler 的程式順序，沒看 middleware 鏈。
- **G2 — 工具鏈細節造成的新缺陷（S1），reviewer 與 tester 各自獨立抓到**：`REQUEST_ID_PATTERN` 帶 `/i`，`@asteasolutions/zod-to-openapi` 9.1.0 只剝掉前後的 `/`，文件裡的 pattern 變成 `…$/i`，任何值都比對不到。執行期不受影響，所以既有測試全綠也看不出來；是 tester 依 issue 要求寫「spec pattern 要接受合法樣本」才紅。兩個 agent 平行做了同一件事的調查。
- **執行面良好之處**：
  - coder 用一次性探針把 35 個舊檢查點全打一遍、逐字比對回應，tester 再把它固化成 table-driven 測試（`worker/tests/integration/paramValidation.test.ts`），讓「回應不變」從一次性證據變成 CI 保證。
  - tester 發現 issue 建議的 grep 樣式（`isValid*(c.req.param(`）對舊程式碼本身就不會紅（舊碼先把 param 讀進區域變數），改用「不准出現 `req.param(`」並附上舊碼 fixture 證明偵測器有效。

## 3 改進提案

- **L0930_1200-1**（對應 G2）`target=.claude/rules/backend.md | sketch=route schema 裡給 OpenAPI 用的 regex 一律不得帶 flag（zod-to-openapi 會把 flag 字面輸出到 pattern）；需要不分大小寫就寫進字元類別。並要求 devTools 測試對每個 path param 用合法樣本驗證 spec pattern | status=proposed`
- **L0930_1200-2**（對應 G1）`target=.claude/rules/change-triage.md | sketch=開 issue 時若主張「會改變 API contract／回應順序」，body 要附上查證過的請求路徑（middleware 鏈 → validator → handler），不能只根據 handler 內的程式順序 | status=proposed`
- **E1**：行為不變的重構，驗收三件套：既有測試零修改全綠＋一次性探針逐字比對所有被改的端點＋把探針固化成 table 測試。本次三者都做了，可沿用。
- **E2**：reviewer 與 tester 平行時，若其中一方先回報了會讓測試紅的缺陷，orchestrator 可以先 SendMessage 通知另一方，避免重複調查（本次沒這樣做，兩邊各花了一段時間在同一個 pattern 上）。
